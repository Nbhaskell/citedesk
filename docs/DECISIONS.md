# Decisions

Decisions the planning documents do not cover. Each entry says what was chosen and why. Newest last.

## Phase 0

### D-001. Defaults for settings the TRD lists without a value
`docs/TRD.md` section 7 names `CITEDESK_DB_PATH`, `OLLAMA_URL`, `SPAM_THRESHOLD` and `DRAFT_MAX_WORDS` but gives no defaults. Chosen:

| Setting | Default | Why |
|---|---|---|
| `CITEDESK_DB_PATH` | `data/citedesk.db` | `data/` is git-ignored, so the database file cannot be committed by accident |
| `OLLAMA_URL` | `http://127.0.0.1:11434` | Ollama's own default address |
| `SPAM_THRESHOLD` | `0.8` | **Provisional.** Nothing exists to measure yet. Revisit in Phase 3 using the `tuned` split only |
| `DRAFT_MAX_WORDS` | `200` | **Provisional.** Revisit in Phase 5 after reading drafts |

### D-002. `/api/status` in Phase 0 reports only what exists
`docs/TRD.md` section 6 describes `/api/status` as model, knowledge base and database health plus the synthetic-data flag. In Phase 0 none of those components exist, so the endpoint returns `status`, `app`, `version`, `synthetic_data`, the configured model name, and a `components` block where each of `database`, `model` and `knowledge_base` is `"not_checked"`. It never reports `ok` for something it did not check. Real checks arrive with the database (Phase 2), the model (Phase 4) and the knowledge base (Phase 5). The response omits URLs and file paths.

### D-003. The server's bind address is a constant, not a setting
`docs/TRD.md` section 8 requires binding to `127.0.0.1` because v1 has no authentication. `python -m citedesk` passes `127.0.0.1` as a constant, and a test checks that no environment variable changes it. Only the port is configurable.

### D-004. Settings use `pydantic-settings`
It reads the environment and `.env`, validates types and ranges, and keeps the exact variable names from the TRD through field aliases. A test checks that `.env.example` lists exactly the settings in code and that its values equal the defaults, so the two cannot drift.

### D-005. Type checker: mypy (strict) on `citedesk/`
The plan allows mypy or pyright. mypy installs with pip, so the toolchain stays pip-only.

### D-006. Lint rules and formatter scope
Ruff lint rules: `E, F, I, B, UP, SIM, S` (the `S` security rules are on; tests may use `assert`). Line length 100. `docs/` and `web/` are excluded from ruff because recent ruff versions also format Markdown code blocks, and the planning documents should not be rewritten by a formatter.

### D-007. Lock files are `pip freeze` output
No lock tool is installed, so `requirements.lock` is the `pip freeze` of a clean runtime-only environment and `requirements-dev.lock` is the freeze of the development environment (runtime plus dev tools). They have no hashes. Regenerate both when `pyproject.toml` dependencies change. The dev lock was made on Windows and includes `colorama`, which is harmless on Linux.

### D-008. CI is tests and lint only
`.github/workflows/ci.yml` runs `ruff check`, `ruff format --check`, `mypy` and `pytest` on Ubuntu with Python 3.13, installing from `requirements-dev.lock`. It does not run the model, the knowledge base or any evaluation. The secret scan runs in pre-commit, as the plan says. First run on GitHub (2026-10-28, commit `5ad8063`) passed in 35 seconds.

### D-009. Secret scan: gitleaks through pre-commit
`.pre-commit-config.yaml` runs the `gitleaks` hook (pinned to `v8.30.1`) on staged files, using the default gitleaks ruleset in `.gitleaks.toml` with no allowlist. It was checked against a deliberately fake token and blocked it. Enable it on a fresh clone with `pre-commit install`.

### D-010. Line endings: LF
`.gitattributes` sets `* text=auto eol=lf` so files are the same on Windows and in CI.

### D-011. `web/` is not scaffolded in Phase 0
No Phase 0 task covers the web app, and the UI is built in Phase 6. `web/` exists as an empty directory so the layout matches `docs/TRD.md` section 3. The `run web` command is filled in when the app exists. The dev server will use a Vite proxy for `/api` to `127.0.0.1:8100` rather than enabling CORS (to be confirmed in Phase 6).

### D-012. `CLAUDE.md` is not tracked yet
`CLAUDE.md`, `CLAUDE.local.md` and `.claude/` are in `.gitignore`. They are assistant-instruction files, and whether to publish them is a separate decision. To track `CLAUDE.md`, remove it from `.gitignore`.

### D-013. Test client dependency
`fastapi.testclient` (Starlette) warns that `httpx` is deprecated for the test client and suggests a package called `httpx2`. It was not adopted: it was not possible to confirm who publishes it, and the warning is harmless today. Revisit if the warning becomes an error.

### D-014. Python version
`pyproject.toml` pins `requires-python = ">=3.13,<3.14"`, matching the stack in the TRD. The machine's default `python` is 3.14, so commands use `py -3.13` to create the virtual environment.

### D-015. Package metadata and install
`pip install -e . --no-deps` after `pip install -r requirements-dev.lock` makes the package importable while keeping the locked versions authoritative.

## Phase 1

### D-016. The demo business is an invented plumbing company, not a pet daycare
`docs/IMPLEMENTATION_PLAN.md` Phase 1 allows reusing the business from `rag-project/demo_docs` or generating a new one with `synthetic-business-universe`. A new one was generated. The original planning documents assumed a pet daycare, so these were changed to match (the schema still wins on names and values):

- `BACKEND_SCHEMA.md`: `service_type` is now `emergency_repair`, `drain_cleaning`, `water_heater`, `fixture_installation`, `inspection`, `other`, `unknown`. `pet_species` is replaced by `property_type` (`house`, `apartment`, `commercial`, `other`, `unknown`). The required-fields table, the `extractions.fields` example and the golden item example were rewritten. `pet_name`, `party_size`, `end_date` and `num_nights` no longer exist as extraction fields. No database column or `CHECK` constraint used these enums, so no migration changes.
- `PRD.md` (FR-7 and two phrases), `UI_UX_DESIGN_BRIEF.md` (mock-ups, the `HEALTH_SAFETY` wording, the sample draft) and `APP_FLOW.md` (one phrase) were updated.
- `address_area` is a new extraction field, required for `booking_request`, because a plumber needs to know whether the job is inside the service area.

Why plumbing: it has clearly bounded safety cases (gas smell, flooding, sewage, carbon monoxide), natural escalations for complaints, disputes and warranty exceptions, and priced jobs that exercise the figure check. The cost is that more inquiries cannot be answered from documents (price depends on diagnosis, availability is live), so fewer end in a fully drafted reply.

**Amendment (same day).** After comparing the fact sheet with the services menu of a real plumbing company's website (used only as a reference for which standard services exist; no names, wording or prices were copied), `service_type` gained `leak_repair` and `sewer_line_repair`, and the fact sheet gained a `services_offered` list, leak detection ($245, invented), and quote-only entries for sewer line repair and slab leak repair. General plumbing repair maps to `other`. Without these, ordinary requests such as "find a leak under my slab" would have escalated as `NOT_IN_KNOWLEDGE_BASE` and the labels would have been ambiguous. `tests/test_universe_facts.py` now checks that every `service_type` in the fact sheet exists in the schema enum, that no offered service clashes with the not-offered list, and that phone numbers and emails follow the synthetic-data rules.

### D-017. Only documents and inquiries are generated from the universe
The `synthetic-business-universe` skill also describes invoices, bookings and reviews. Citedesk needs none of them, so only `universe/facts.json`, the knowledge-base documents and the labelled inquiries are generated.

### D-019. Knowledge-base documents are generated and checked, never hand-edited
`tools/generate_kb_docs.py` renders eight documents (`about`, `emergencies`, `faq`, `hours`, `policies`, `pricing`, `service-area`, `services`) from `universe/facts.json`. They are deterministic, so there is no seed. `tools/check_consistency.py` fails if any dollar amount, percentage, time, date, phone number or email in a document is not in the fact sheet, and if any priced fact, service, closed date, staff name or not-offered item is missing from its document. Other numbers must at least appear somewhere in the fact sheet (a weak check; it catches invented figures such as "48 hours" but not a wrong-but-existing number). The generator refuses to write files if the check fails. Tests cover the generator and include deliberately wrong documents (wrong price, wrong time, wrong date, invented total, unknown phone and email, dropped items) to prove the checker catches them. The committed documents are also tested against a fresh render so they cannot drift.

Documents never refer to themselves ("see the Pricing document"), because that would teach the drafting model to write "according to the documents", which the `STRUCTURE` check bans. Headings follow the schema example (`pricing.md > Drain cleaning`).

Reading the output as a customer found fragments and a duplicated sentence caused by pasting fact-sheet text into sentences. Those were fixed in the generator, and the gas-smell instruction in the fact sheet was shortened so it no longer repeats "does not do gas work".

### D-020. No PDF document yet
The skill suggests one short PDF. `rag-project` does read PDFs (its passages carry a `page` number), so nothing blocks one, but no inquiry scenario needs it. Skipped; revisit only if page-number citations should be tested.

### D-021. What running rag-project showed (details in `docs/knowledge-base-contract.md`)
- **`/api/ask` has enough structure** for `retrievals.sources` (TRD open question 1: yes). There is no decline flag. `sources` is empty on a refusal, but not always: one "I don't know" answer still listed sources, and the same question gave different results on different runs. Phase 5 must decide the adapter's decline rule; a candidate (empty `sources`, or a refusal phrase in the first sentence, in code) is recorded in the contract.
- **Availability questions return partial answers, not declines.** They must be handled in code, not left to the knowledge base.
- **The not-offered list was restructured** into one short section per excluded service, following rag-project's own advice (one topic per section). On nine ad-hoc questions the exclusion passage reached the top 4 for 8 of 9 items, up from 0 of 9. One wrong answer remains (a restaurant is still said to be servable). It was **left unfixed on purpose**: editing the documents to fix a question that was written to probe them would be tuning to the test itself. Code routing on `property_type = commercial` and the Phase 5 checks are the intended defence. Expect this to appear in the evaluation and in the README's "where it goes wrong".
- **Question logging in rag-project is on by default.** Citedesk runs it with `RAG_LOG=0` so customer-derived questions are not written to its logs.
- Recorded responses are in `tests/fixtures/` for the Phase 5 contract test. They prove only that the format parses.

### D-022. Golden-set design (details in `eval/golden/README.md`)
- **Shape extended.** `BACKEND_SCHEMA.md` section 8 gave an item shape without a `category`, although the Phase 1 acceptance check asks for counts per category. Added: `category`, `evidence` (`{file, anchor}`, matched by text and verified against the documents), optional `sender_email`, optional `contains_sensitive_data`, a file header (name, version, reference date, author, document hash, counts). Section 8 was updated to match. The two documents were in tension here; the schema file wins on names, so it was changed rather than worked around.
- **Source of truth for enums is `docs/BACKEND_SCHEMA.md` for now.** `tools/golden.py` reads the enum rows from that file. Phase 2 creates `citedesk/models.py`; switch the import then. The required-fields table in `tools/golden.py` is likewise temporary and should be tested against `routing.py` in Phase 4.
- **Labels cannot disagree with the rules.** `expected_route` is derived from the labels by the TRD 4.3 rules and must match; `should_escalate` must equal "route is escalate"; `health_or_safety` requires `HEALTH_SAFETY`; `complaint` requires `COMPLAINT`; `NOT_IN_KNOWLEDGE_BASE` is only valid on the draft path.
- **Sender-email matching is unavailable in v1.** `BACKEND_SCHEMA.md` section 2 says a booking change or cancellation needs a booking reference "or sender email match", but the schema has no customer or booking table to match against. The golden set treats it as never matching, so a change or cancellation without a reference gets `request_details`. If a customer table is added later, revisit.
- **Emergencies are `health_or_safety`.** Gas smell, carbon monoxide, flooding, a burst pipe and sewage backup all carry `HEALTH_SAFETY` and `urgent`, and are escalated, not drafted. This is a labelling choice: a burst pipe is property damage rather than a health risk, but the owner should see it first and the queue shows urgent escalations at the top.
- **Hand-written, not generated.** The messiness (typos, run-ons, inconsistent dates) is written into the text rather than injected by a seeded script, because a script corrupts the facts the labels depend on. There is therefore no seed; the committed files are the data. The author is recorded in the file header.
- **Relative dates are null.** "Next Tuesday" and "this week" are ambiguous, so `start_date` is null and details are requested.
- The TRD's safety-net keyword examples were still pet-themed after the business change and have been replaced with plumbing terms.

### D-023. The tuned golden set: 135 items (details in `eval/golden/README.md`)
All 13 intents, all 18 categories and every escalation reason a labeller can know in advance are covered; `UNVERIFIED_FIGURE` and `MANUAL` appear at zero because they come from draft checks and reviewers, not from the message. `booking_flow` has 11 items instead of the planned 12 and `unanswerable` 7; the total is within the planned "about two thirds of 200".

Two findings from writing it that need a decision and were not changed:
- **Gas water heaters.** The fact sheet prices water heater replacement but excludes "gas line or gas appliance work". A gas-fired heater is on that line. Recorded as an unanswerable item rather than resolved.
- **Commercial property has no routing rule.** The TRD routes only on reason codes, missing fields and spam; a complete booking request for a commercial building gets `draft_reply`, and only the knowledge base (which D-021 showed can say "yes") stands between the customer and a wrong answer. Phase 4 should decide whether to add a rule.

Small counts per label (for example 8 safety items, 2 legal threats) mean per-reason scores will be noisy; the evaluation report must say so.

### D-024. `tools/import_inquiries.py` and the intake payload it assumes (confirmed against the real API in Phase 3; see D-034)
`docs/TRD.md` section 6 names `POST /api/inquiries` but gives no request shape. The import tool posts `external_id`, `channel`, `sender_name`, `body`, and optionally `sender_email` and `subject`, as JSON. **This is an assumption**: Phase 3 builds the endpoint and should either accept this payload or change the tool. It was tested against a stand-in HTTP server on loopback and a fake transport, not against the real API, which does not exist yet. It treats HTTP 200 and 201 as created, 409 as already imported (the schema's unique index on `channel` plus `external_id` suggests the endpoint will say so), and anything else, or no connection, as a failure.

Rules built into the tool and covered by tests: labels, notes, categories and evidence are never sent; any address other than `127.0.0.1`, `localhost` or `[::1]` over `http` is refused; output contains ids and counts, never message text (rule 4 in `docs/RULES.md`); an inbox line with an unknown field is rejected, so a labelled file cannot be posted by mistake.

### D-018. Safety advice is a closed list in the fact sheet
`universe/facts.json` has a `safety_instructions` block (shut off the main water valve; gas smell; sewage backup; carbon monoxide alarm). It is the only advice a reply may contain. Anything else about fixing a problem goes to a person. How these replies are produced (a fixed template or a checked draft) is to be decided in Phase 4 or 5 when routing and drafting are built.

## Process

### D-025. One branch and one pull request per phase, from Phase 2
Phases 0 and 1 were committed directly to `main` and stay there. From Phase 2, each phase is built on its own branch (`phase-2-data-layer`, `phase-3-intake-screening`, and so on) with the usual small commits, one per task. At the phase's acceptance check the branch is pushed and a pull request is opened. Its description lists what was built, what passed, and anything unverified or assumed. CI must be green, and merging is a manual step. Why: CI then runs before code reaches `main`, and each phase becomes one page to review, with its acceptance check written down. Nothing is pushed and no pull request is opened until a push is requested. The branch only exists to hold the work; `main` is unchanged until the merge.

## Phase 2

### D-026. Database conventions and what the migration runner cannot do
`citedesk.db.connect` opens SQLite in autocommit mode (`isolation_level=None`) with foreign keys on, rows as mappings, and WAL for file databases. Grouped statements use `transaction()`, which commits on success, rolls back on any exception, and joins an open transaction. Each migration runs in its own transaction together with its `schema_migrations` row, so a failure leaves nothing half applied. `0001_init.sql` is extracted from the SQL block in `BACKEND_SCHEMA.md` and a test compares them character for character.

Limits worth knowing: `schema_migrations` has no checksum column (the schema document defines it exactly), so editing an already-applied migration is **not detected**; "never edit an applied migration" stays a convention. The runner refuses a gap in numbering, a duplicate number, a badly named file, and a database newer than the code. Connections use SQLite's default `check_same_thread`, so Phase 3 must open one connection per request or worker rather than share one across FastAPI threads.

### D-027. Models and the enum checks
`citedesk/models.py` holds every enum and one row model per table. Four enums are not in the schema's section 1 table but are needed: `ScreeningResult`, `EscalationSource` and `ExportMethod` (values from `CHECK` constraints) and `AuditEventType` (from a comment on `audit_events.event_type`, which has no `CHECK`). Tests read the `CHECK` constraints back out of a migrated database and compare them with the enums, compare the enums with the schema document's table, require a row model for every table whose fields equal its columns, and fail if an enum exists that none of those sources accounts for. `Channel.import_` has a trailing underscore because `import` is a Python keyword; its value is still `"import"`. `tools/golden.py` now takes its enums from here.

### D-028. Repository rules that go beyond the schema
- `update_inquiry` cannot change `status` (or the message); only `state.transition` does, and a test fails if any other module writes `inquiries.status`.
- A new draft starts as **`blocked`**, not the database default `ready`: a draft is not ready until its checks have run. `set_draft_status` refuses `ready` or `approved` while any blocking check has failed, raising `DraftBlocked`. This enforces "no draft with a failed blocking check is ever marked ready" at the data layer, as a floor under whatever the Phase 5 pipeline does.
- Re-running a stage is safe: screenings and draft checks are upserts, and an open escalation with the same reason is reused instead of duplicated.
- An extraction must belong to a classification of the same inquiry; an escalation `detail` is capped at 200 characters.

### D-029. State machine details, and two gaps in the schema's table
`citedesk/state.py` holds the 20 allowed moves, written out in code and compared in a test with the table in `BACKEND_SCHEMA.md` section 5; every one of the 169 status pairs is tested. The "failed returns to the prior stage's input status" row needs a mapping, chosen here: failed at `screen` returns to `received`, `understand` to `screened`, `retrieve` or `draft` to `routed`. Each status may fail only at its own stages. A failure message is capped at 300 characters and may not contain a 20-character run of the customer's own words. `transition()` updates the status, sets or clears the failure fields, and writes the `status_changed` event in one transaction.

**Gap for Phases 4 and 5:** the table has no way to fail from `classified` (so a crash in the route stage) or from `drafted` (a crash in the check stage). If the pipeline needs either, `BACKEND_SCHEMA.md` section 5 and `state.py` must change together; do not catch the error and leave the inquiry stuck.

### D-030. Audit events: what counts as message text, and what this cannot catch
`events.record_event` is the only writer of `audit_events` (a test enforces it). A payload must be flat; keys are snake_case names; values are numbers, booleans, null, or short code-like tokens (no spaces, at most 64 characters, no `@` or `/`, no phone-like digits) or flat lists of those. A token that appears as a whole word in that inquiry's own body, subject, sender name or email is refused unless it is a known code from the enums. A rejection never repeats the rejected value, because the exception may be logged. This blocks sentences and single words lifted from the message. It cannot catch a paraphrase, a word from a different inquiry, or a harmless-looking token that happens to be sensitive. The structured log helper in the TRD's `events.py` is not written yet; it should reuse `validate_payload` when the pipeline needs it (Phase 3), and Phase 8 verifies logs.

## Phase 3

### D-031. Screening runs at intake, before the first write
The documents say both "mask sensitive values before the body is stored" (TRD 4.1) and "write the inquiry with status `received` before any processing" (APP_FLOW 4.1). Read literally they conflict: masking is processing. Resolved as follows. `intake.submit` runs the screening detectors (pure code, milliseconds, no model) and writes the inquiry and its `screenings` row in **one transaction**, with the body already masked. The pipeline's screen stage then applies the stored result. So an unmasked number is never on disk, not even for a moment, and everything slow (the model, the knowledge base) still happens after the write. If screening itself crashes, intake stores **nothing** and returns a 500: refusing is safer than keeping text that was never checked, at the price that the caller must retry. Tests look at every cell of every table for the original card digits.

### D-032. The detectors, what they flag, and what they deliberately do not
All are pure functions in `citedesk/screening.py`; results hold pattern names, never matched text.
- **Card numbers:** 13 to 19 digits, either contiguous or grouped like a card (4-4-4-4, 4-6-5), passing the Luhn check, and not a single repeated digit. Masked as `**** **** **** 1111` (last four kept). A 16-digit invoice number that fails Luhn is left alone. About one in ten random 16-digit numbers passes Luhn, so a coincidental order number will occasionally be masked; that is the safe direction.
- **Government IDs:** **TRD 4.1 says "the authoritative lists of values are in `BACKEND_SCHEMA.md`", but that file has no such list.** Chosen: US Social Security numbers only, either formatted (`123-45-6789` or with spaces) with the structural rules (area not 000, 666 or 9xx; group not 00; serial not 0000), or nine bare digits within a few characters of "SSN" or "social security". Passports, driving licences and bank numbers are not covered; say so in the README.
- **Injection:** a message is flagged if any *strong* pattern matches (ignore previous instructions, reveal the system prompt, persona swap, "do not tell staff", decode-and-follow), or if two different *weak* patterns appear together (claims to be the owner, "I authorise you to", a JSON reply template, "format your reply as JSON", "reply that ... is confirmed"). Base64 blobs are decoded and the strong patterns run on the result. **Not flagged on purpose**, because real customers write them: "ignore my earlier message", "I am the owner of the house", "I authorise you to go ahead", "you are now my favourite plumber", "give me instructions for the main valve". A customer who writes "ignore the previous instructions" about their own request will be escalated; a person reads it.
- **Spam:** a weighted score (spam phrases, links, link-only text, runs of "!", capital letters, money hype, a phishing combination, and no plumbing vocabulary). Capital letters alone add 0.1, so an urgent message in capitals can never be archived. The threshold stays at the provisional 0.8 (D-001). Injection beats spam; an emergency term vetoes archiving; a sender with an earlier clean inquiry (the only definition of "known customer" v1 can support, since there is no customer table) is not archived.
- **Result on the tuned golden set:** every spam item scores at least 0.90 and no real inquiry scores above 0.20; exactly the six labelled injection items are flagged, none of the near-misses; the one card number is masked and the Luhn-failing invoice number is not. **These detectors were written with that set in view**, so this shows the machinery works, not how it generalises. The held-out set is the honest test.
- **For Phase 4:** the emergency keyword net over-fires on two items that mention past events ("flooded my kitchen" in a legal threat, "a pipe burst last month") and misses one safety item that never uses a keyword (sewage on the laundry floor). Both are measurable on the golden set.

### D-033. Intake rules the documents left open
Limits: body 1 to 10,000 characters (`MAX_BODY_CHARS`), subject 300, sender name and ids 200, email 254. Control characters are removed, line breaks kept; emails are lower-cased; `received_at` is normalised to UTC and refused if more than five minutes in the future. A repeated `(channel, external_id)` is refused with 409 and the existing id. **Duplicate window: 24 hours** (`DUPLICATE_WINDOW_HOURS`, 0 turns it off): the same sender (email, or name if there is no email) sending the same subject and body after masking and normalising case and spacing. A duplicate is stored as its own row with `duplicate_of` set, then the screen stage archives it. **This differs from APP_FLOW 4.1**, which says duplicates show "in the queue": the review queue lists only `needs_review`, `escalated` and `failed`, so a duplicate appears under the archived filter and in the original's detail (`duplicates`), not in the queue itself.

### D-034. API choices
One error shape `{error: {code, message, request_id}}` on every failure, with an `X-Request-ID` header on every response; messages never repeat what the caller sent (field names only). A database connection is opened inside each request, because FastAPI may run a dependency and its endpoint on different threads and SQLite connections are thread-bound. `POST /api/inquiries/import` takes the file as the **raw request body** (`application/x-ndjson` or `text/csv`, 5 MB, 5,000 records) rather than a multipart upload, which would need an extra dependency; a bad line never stops the others and the summary holds line numbers and codes only. Lists use keyset paging in review-queue order, so new arrivals cannot make a page skip or repeat a row. `/api/status` now checks the database and reports queue depth and whether the worker runs; model and knowledge base stay `not_checked`. Webhooks use the same endpoint with `channel: webhook`. **Settles D-024:** the real import tool, run against the real server, stored all 135 messages and treats 409 as "already imported". Not built yet, by design: reprocess, drafts, review decisions, export and insights (later phases).

### D-035. The worker, and what is not logged
The screen stage does all its work (status changes, escalations, route, audit events) in one transaction, so a crash leaves the inquiry at `received`, where it can fail cleanly with `failure_stage = screen` (the state table allows nothing else; see D-029). The stage is retried once, then the inquiry is marked `failed` with a message naming only the exception type. The worker thread polls every two seconds and wakes on each new inquiry; one worker per process, one inquiry at a time, and a second process would be safe because the status is checked inside the transaction. Suspected-injection items get route `escalate` but no urgency unless an emergency term is present (then `HEALTH_SAFETY` and `urgent`), because no model reads them. No structured log helper exists yet: the code logs only ids and exception type names, and Phase 8 verifies that no message text reaches a log.

## Phase 4

### D-036. A failed route stage: `classified` to `failed` (settles the first gap in D-029)
The state table had no way to fail from `classified`, so a crash in the route stage would have left an inquiry stuck there with the worker retrying it forever. Added `classified` → `failed` ("route stage crashed after retry") to `BACKEND_SCHEMA.md` section 5, `state.py` (`ALLOWED`, and `RETRY_TARGET[route] = classified`) and the state tests, together, as D-029 asked. A retry returns to `classified`. The second gap in D-029 (`drafted` has no failure move, for a crash in the check stage) is **left open on purpose**: nothing in Phase 4 needs it, and a test now pins that `drafted` still refuses to fail, so Phase 5 has to decide it knowingly.

### D-037. The emergency net, extended and measured (`citedesk/safety.py`)
D-032 named three disagreements between the net and the tuned golden set: it fired on two items that mention something past, and missed `safety-sewage-on-laundry-floor`, which never uses a keyword. Two changes, both in code and covered by tests:

- **Sewage can be described instead of named.** Foul water on a floor ("dirty smelly water ... on the laundry room floor"), toilet paper next to a floor, tub, shower, sink or drain, water "coming up out of" a floor drain, toilet, tub or shower, and a toilet that overflows. Ordinary drain talk does not fire (a slow or gurgling sink, a toilet-paper holder, brown tap water, bubbles in a toilet when the washer drains); the tests list these near-misses.
- **A historical mention is discounted.** A match is dropped if its own clause says it was long ago ("last month", "two years ago", "back in 2019", "the last time") and does not also say it is happening again ("again", "still", "today", "this morning"). A clause ends at punctuation or at "and", "but", "so", "because", "now", "please", "then", so "flooded last year please help water everywhere" still fires on the second half. "Last week" and "last night" are **not** historical: that water may still be there.

**Measured on the tuned split (135 items, label `HEALTH_SAFETY` against "the net fired"):** before, 7 of 8 safety items caught, 2 over-fires; after, 8 of 8 caught, 1 over-fire. The remaining over-fire is `legal-sue-over-water-damage` ("your plumber's repair failed on Sunday night and flooded my kitchen"): nothing in the clause says it is over, so it fires. It escalates for `LEGAL_THREAT` anyway, so the route is unchanged; the extra `HEALTH_SAFETY` reason and `high` urgency are noise the reviewer will see. A test pins exactly this one item.

**What this cannot tell you.** The net was extended with these items in view, so 8 of 8 shows the rules agree with the labels, not how well they generalise; eight safety items cannot bound a miss rate much better than "up to about one in three". Hypotheticals and prevention ("to stop pipes bursting this winter", "in case of a flood") are not discounted; they fire and a person looks. A historical marker in a different sentence from the term ("The pipe burst. That was last month.") does not discount it.

**What the net does with a hit (TRD 4.2, as written):** urgency is raised to **at least `high`** and `HEALTH_SAFETY` is added with source `safety_net` when the model did not already flag it. This differs from D-035, where a suspected-injection item with an emergency term gets `urgent`: there no model reads the message, so the net is all there is. Where a model has read it, the model's own `urgent` is kept and the net is only a floor.

### D-038. Routing rules (`citedesk/routing.py`): where the rules go beyond TRD 4.3
`decide_route` is a pure function of the intent list, the primary confidence, the extracted fields, the codes the model flagged (D-041), the screening result, whether the emergency net fired, and the low-confidence switch. Urgency is deliberately not an input: it orders the queue and does not route. Tests cover each rule alone, the order, and a set of invariants checked over the whole cross product of the inputs (about 54,000 combinations), plus every tuned golden item.

Choices the documents left open:
- **Archive needs the model to agree, and nothing else to apply.** TRD rule 1 is "spam score above threshold and no non-spam intent". Here the screening result must be `spam`, every classified intent must be `spam`, and no escalation reason may apply (so an emergency term, a legal threat or low confidence beats the archive). The only inquiries that reach this rule are from known senders, because the screen stage already archives the rest.
- **A model that says "spam" when screening does not is sent to a person.** TRD 4.3 would draft a reply to it (no rule matches). Archiving on the model's word alone is not allowed (a mistaken archive loses a customer's message), and drafting a reply to spam is wasted work that ends in `NOT_IN_KNOWLEDGE_BASE` anyway. The reason code is `LOW_CONFIDENCE`: the model and the screening disagree. This rule ignores the low-confidence switch. It is the nearest fit among the existing codes, not an exact one.
- **Only the primary intent's confidence escalates.** A low-confidence guess at a secondary intent does not.
- **Missing means null, blank or "unknown"** (the model's word for a value it could not find). `property_type: unknown` on a booking request therefore asks for details.
- **The net is credited only when it alone raised `HEALTH_SAFETY`.** If the model also classified the message as health or safety the reason's source is `rule`.
- **Every matching reason is recorded**, in the order of the reason-code list in `BACKEND_SCHEMA.md`. A reason raised twice (for example `POLICY_EXCEPTION_REQUEST` flagged by the model and by a commercial property) is one reason with both details. Missing fields are reported even when the route is `escalate`, so the reviewer sees what was absent.

### D-039. Commercial property escalates
The business serves homes and small residential buildings up to four units, and says so in three documents. D-021 showed that the knowledge base can answer "yes" to a restaurant, and D-023 noted that no rule looked at `property_type`, so a complete booking request for a dental office would have been drafted. Rule: **any inquiry whose extracted `property_type` is `commercial` escalates with `POLICY_EXCEPTION_REQUEST`** (source `rule`, detail "commercial property; the business serves homes only"), whatever the intent. Serving a commercial building would be an exception only the owner can grant, which is the code's own definition in the golden README.

- **Why any intent and not only bookings.** `oos-cafe-grease-trap` only asks "do you do work for businesses or just homes?", which the FAQ answers with a plain no. It escalates too: that is the question the knowledge base is known to get wrong, and the cost of escalating is one line the owner types.
- **It is a stretch of the code's meaning.** There is no reason code for "outside what we do". The alternatives are `MANUAL` (reserved for a reviewer's own escalation) or a new code, which means a migration of the `CHECK` constraint and every document that lists the codes. A new code may be preferred; until then the reviewer reads the detail line.
- **Labels follow the rule, not a model result.** The two golden items were relabelled `escalate` / `POLICY_EXCEPTION_REQUEST` and the validator now requires that code on any commercial item. This was done before any model ran on them.
- **Not covered:** other things the business does not serve (a 12-unit building extracted as `apartment`, a church extracted as `other`). Only the extracted `commercial` value triggers the rule, so it is as good as the model's extraction.

### D-040. One required-fields table, in `routing.py` (settles the temporary table in D-022)
`tools/golden.py` no longer keeps its own copy of the table or its own `missing_fields`; it imports both from `citedesk/routing.py`, so there is nothing left to drift apart. The agreement D-022 asked a test to check is now between the table and `BACKEND_SCHEMA.md` section 2 (`tests/test_routing.py` parses the document), and between the routing code and every golden label (`tests/test_routing_golden.py`). One known difference from the document: for a booking change or a cancellation it allows "a booking reference or sender email match"; v1 has no customer table, so the code requires the reference (as D-022 already decided for the labels).

### D-041. Where `REFUND_OR_DISPUTE`, `LEGAL_THREAT` and `POLICY_EXCEPTION_REQUEST` come from (the documents are silent)
`TRD.md` 4.3 lists these three as escalation reasons, but nothing says how they are detected: the model's output (TRD 4.2) has intents, urgency, sentiment and fields, and the `intent` list has no value for any of them. `HEALTH_SAFETY` and `COMPLAINT` have intents; these three do not. Decision: the model returns an extra field, **`escalation_signals`**, a list drawn from exactly these three codes (the schema enum, and `routing.decide_route` refuses any other code). It reads and flags; **code escalates on any flag and nothing the model says can remove one**, so "the model reads, code decides" still holds. The flags are not in a database column (the schema has none); they live in `classifications.raw_response`, and the route stage parses them back from there, so a re-route needs no model call.

**What this cannot do.** If the model misses a flag, nothing in Phase 4 catches it: there is no keyword net for these three the way there is for emergencies. Phase 5's `NO_COMMITMENT` check is a second line for exception requests that reach a draft; nothing is for a missed legal threat or refund demand. The baseline reports recall for each, and if it is weak a keyword net (lawyer, sue, small claims, chargeback, refund) is the obvious next step. It was not built now because there is no measurement yet to justify its false positives.

### D-042. The understand step (`citedesk/understand.py`, prompt `understand-v1`)
- **Prompt.** Written from the labelling rules in `eval/golden/README.md` (the definitions a human labeller uses), not from looking at items, and without examples; a test fails if any 30-character run of a golden message appears in it. The sender's name and email are not sent: they do not help classify. The message sits in `<inquiry>` tags that the prompt says hold data only; anything in the text shaped like those tags is removed first. Injection-flagged messages never reach the model (D-032).
- **Output.** One JSON object validated by Pydantic (`UnderstandOutput`): `summary`, `intents` (1 to 5, no repeats), `primary_intent` (must be among them), `urgency`, `sentiment`, `escalation_signals`, `fields` (all seven keys). The same class produces the JSON schema sent to Ollama's `format`, with every `$ref` inlined so a grammar can be built from it. Checked against the live server: the grammar is accepted and replies are valid JSON.
- **Retry.** Two attempts. An invalid reply is retried with the field-level problem appended (never the model's own words); a timeout, refused connection or unusable reply is retried with the same prompt; a reply cut off by the token cap counts as invalid. With `ENABLE_THINKING` on, the first attempt thinks and the retry does not. `LLMProvider.generate_json` therefore gained a `think` argument beyond the TRD's signature. Temperature 0, seed 0, 1,500 tokens, 120 seconds; the context window is set to 8,192 tokens because Ollama's own default silently drops the start of a long prompt, and the provider refuses a reply whose prompt came within 64 tokens of the limit. A normal prompt is about 950 tokens.
- **Code after the model.** A visit date must be a real date and not before the day the message arrived, otherwise it is dropped (`start_date_invalid`, `start_date_in_past`) and the customer's own words stay in `dates_as_written`. Free-text fields are trimmed and capped; the placeholder words the model writes when the customer said nothing ("unknown", "n/a", "none") become null (seen in the first live run). Required fields are computed from the table in `routing.py`.
- **What is stored.** `classifications.raw_response` is the model's accepted reply exactly as it came; `classifications.urgency` and `inquiries.urgency` hold the urgency **after** the emergency net (the model's own value is still in `raw_response`); `safety_net_hit` is 1 whenever the net fired, even if the model had already said urgent. `classifications.attempt` counts runs of the stage, not retries, because only an accepted reply is stored.
- **Recorded reply.** `tests/fixtures/ollama_chat_response.json` is one real `/api/chat` reply to an invented message, replayed in a contract test (TRD section 10). It shows the format parses and nothing more.

### D-043. The understand and route stages, and what happens when they fail (`citedesk/pipeline.py`)
- **Where each inquiry rests.** After the route stage an inquiry is `escalated`, `archived`, or `routed`. A `routed` inquiry (route `draft_reply` or `request_details`) waits for Phase 5; nothing picks it up yet.
- **The model is called with no transaction open.** The understand stage records `stage_started`, waits for the model (up to two attempts of 120 seconds), and only then writes the classification, extraction, urgency, status change and `stage_finished` event in one transaction. Holding SQLite's write lock for a minute would block the API's intake. A test checks `in_transaction` is false during the call. The route stage never calls the model and does everything in one transaction, as the screen stage does.
- **Failure.** A model that gives no usable reply has already had its retry inside the understand step, so the stage is not run a second time: the inquiry goes to `failed` with `failure_stage = understand` and a message like "The model gave no usable reply (timeout)". Any other crash (a database error, a bug) runs the stage once more, then fails as "Understanding crashed twice (RuntimeError)" or "Routing crashed twice (RuntimeError)". A `stage_failed` event records the reason code and the attempts. Messages and events hold codes and exception type names only. With Ollama stopped, every inquiry fails within seconds, not minutes, and stays `failed`; `run_pending` does not retry failed inquiries, because a retry has to be deliberate (the state machine allows it; the endpoint for it is a later phase).
- **No model, no understanding.** `process`, `run_pending` and `PipelineWorker` take an optional model; without one they only screen, as in Phase 3. The library and the tests never attach one. `python -m citedesk` attaches Ollama, in one place (`__main__.py`). An autouse test fixture makes any test that reaches the real Ollama call fail, so the suite cannot need a model by accident.
- **Reasons the pipeline cannot give for injection items.** The model never reads a message screening flagged (TRD 4.1), so a refund demand inside an injection attempt (`injection-claimed-owner-refund`) is escalated for `INJECTION_SUSPECTED` only. The golden label lists both, which is what should be true of the message; the scoring script reports the difference instead of hiding it.
- **Audit events.** `stage_started`, `stage_finished`, `route_decided` (route, reason codes, missing fields, whether the net fired) and `stage_failed` hold codes only. The field names that can appear as "missing" and the failure reasons were added to the events module's list of known codes, so a customer who happens to write "timeout" or "start_date" cannot make an audit write fail.

## Phase 5

### D-045. Retrieval: the decline rule, the questions, and live availability (`knowledge.py`, `retrieval.py`)
- **Decline rule** (the candidate in `docs/knowledge-base-contract.md`): a reply from rag-project is a decline when it lists **no sources**, or when its **first sentence is a refusal** ("I don't know", "I'm not sure", "the documents do not say", "I cannot find", "there is no information", an empty answer). Only the first sentence is read, so "Standard visits are 2 to 4 days out. I don't know the exact day." is an answer. A decline by refusal keeps the passages it listed so a reviewer can see what was found. The phrase list is plain code with tests; it will miss a refusal worded another way.
- **Sources** are the passages rag-project marked `listed`, one entry per passage (so one file can appear twice), best first. Merged across questions without repeats; a declined question contributes none.
- **Questions are built in code, not by the model**, one per askable intent, at most three: fixed wording for prices ("How much does drain cleaning cost?"), booking ("What is needed to book ... and how does booking work?"), changing and cancelling; the open intents (policy, service, billing, other) carry the customer's own question sentences (at most two, 300 characters), prefixed with the service if known. Health and safety, complaints, spam, partnerships and availability are never asked. When the route is `request_details` the booking-process questions are skipped, because the reply already asks for the missing details.
- **Live availability is decided in code.** The knowledge base answered an availability question with a partial answer that reads as helpful (contract, finding 1), and the golden set expects such an item (`unanswerable-availability-friday-complete`) to end in `NOT_IN_KNOWLEDGE_BASE`. An `availability_question` intent is therefore never sent to it. If nothing else was asked, nothing grounded exists and the inquiry escalates with that reason and a holding reply; if other questions were asked, the model's prompt says a member of the team will confirm availability and the draft check blocks any confirmation.
- **The knowledge base and the question stay on this machine.** `RagProjectKB` refuses a non-loopback address, as the model's provider does, and its errors never repeat the question.

### D-046. The draft checks (`checks.py`): what each can and cannot catch
All five run on every draft; `ADDRESSES_ASK` is not implemented (TRD: off by default, not a gate until calibrated). Blocking: `FIGURES_GROUNDED` (-> `UNVERIFIED_FIGURE`), `NO_COMMITMENT` (-> `POLICY_EXCEPTION_REQUEST`), `NO_INJECTION_ECHO` (-> `INJECTION_SUSPECTED`), as in `APP_FLOW.md` 4.6. Warnings: `STRUCTURE`, `CLAIMS_HAVE_SOURCES`.
- **Figures.** Money, dates (ISO, "Nov 6th", "6 November"), times ("7:30 am", "5 pm", "noon"), phone numbers, percentages, weekdays and other numbers, with spelled-out numbers from two to twelve ("one" is not counted: it is too often just a word). A figure is grounded if it appears in the sources, the customer's own message, or the business's contact details from the fact sheet (name, two phone numbers, email). **Money must match as money**: "$2" is not grounded by "2 to 4 business days". A bare number is grounded by any number, price or percentage with that value. A sum of two source prices (a price with itself allowed) is `derived`: shown, not blocked. **What it cannot do:** it compares values, not meaning, so "$149" attached to the wrong service passes; a bare number matching an unrelated number passes; a correct figure written as a word above twelve is flagged.
- **Commitments** are phrase lists in four groups (booking confirmed, refund, discount or waiver, guarantee) plus two for advice (safety actions such as "turn off", "leave the building", "call 911", and reassurance such as "it is safe"). A match is excused when the same words appear in the sources (a quoted policy), or when negation or "if/once/until/unless" comes earlier in the same sentence ("we cannot guarantee", "once it is confirmed", "no visit is confirmed until..."). **What it cannot do:** a promise worded some other way passes, and an excuse word earlier in a sentence can hide a real promise ("not only will we refund you").
- **Structure.** A greeting at the start, a sign-off in the last three lines, no more than `DRAFT_MAX_WORDS` words (200), and no internal wording: "according to the documents", "the knowledge base", "the provided context", "as an AI", "source 2", or any intent, reason, check or service code with an underscore.
- **Claims.** Every claim must point at a source index that exists, and a model-written reply with no claims at all is flagged (it states facts from nowhere). Templates are exempt.
- **Injection echo.** Fails if the draft repeats 40 characters of the system prompt, contains wording the screening detectors call injection, or contains a web address or email address that is not in the sources or the business's own details. A link the customer sent is not allowed back out.
- Checks only report. The data layer still refuses to make a draft `ready` while a blocking check has failed (D-028).

### D-047. Drafting (`drafting.py`, prompt `draft-v1`)
- **Three kinds of draft.** A model-written `reply` (from the retrieved passages only); a `request_details` reply that is a **plain template** when there is nothing to answer, asking only for the missing fields (TRD 4.3 lists the template; no model is used); and a `holding_reply` template when the knowledge base cannot answer, which promises a person's answer and nothing more. For `request_details` with answerable questions the model writes the reply and is told which details to ask for. Templates carry model `template` and prompt version `template-v1`.
- **Prompt.** States the rules the checks enforce (passages only; never confirm a booking; no figure not in the passages or the message, no totals; no refund, discount, exception or guarantee; no health or safety advice unless a passage says it; do not mention documents or the system), puts the message and the passages in tags it says hold data, numbers the passages from 0 so `claims` can point at them, and says in plain words what the passages do not cover and which details to ask for. A test fails if a golden message appears in it. Temperature 0.2 (TRD: at most), seed 0, 800 tokens, thinking off, two attempts as in the understand step (`DraftFailed`).
- **Greeting.** The first plain name in the sender's name ("Dr." and similar are skipped); a name that looks like an instruction, has digits, or is over 30 characters is ignored and the draft says "Hello,". The reply subject is "Re: " plus the customer's subject, capped at 120 characters.
- **Card and ID numbers.** When screening masked one, every draft is told to, or does, ask the customer not to send them by email (APP_FLOW edge cases).
- **Settings.** `BUSINESS_FACTS_PATH` (default `universe/facts.json`) is where the business name and contact details come from.

### D-048. A crashed check stage: `drafted` to `failed` (settles the second gap in D-029)
Same reasoning as D-036: without it a crash in the check stage would leave the inquiry stuck at `drafted`. Added `drafted` -> `failed` ("check stage crashed after retry") to `BACKEND_SCHEMA.md` section 5, `state.py` (`RETRY_TARGET[check] = drafted`) and the tests; a retry returns to `drafted`. `needs_review` now stands in the test of a status with no failure move.

### D-049. First real run of stages 1 to 6, and a manual read of 30 drafts
One run of `python -m tools.run_pipeline` on the tuned split: `understand-v1` and `draft-v1`, `qwen3:8b` through Ollama, rag-project at `127.0.0.1:8000` (thinking on, its default) with Citedesk's 8 documents (83 chunks), run id `pipeline-v1-tuned-20261028-220018`, commit `75eb682`. **Nothing was tuned after seeing it**; the three code defects below were fixed because they are check bugs, and the prompt, the question builder and the routing were left as they are.

**Outcome.** 135 items, 0 failed, 38 minutes (about 17 s per item). `needs_review` 76 (52 model-written replies, 24 requests for details), `escalated` 53, `archived` 6. 92 drafts: 55 model-written replies, 24 requests for details (18 plain templates, 6 written by the model because the message also asked something the knowledge base answered), 13 holding replies (templates); 89 `ready`, 3 `blocked`. Blocking checks failed on 3 drafts (`NO_COMMITMENT` twice, `NO_INJECTION_ECHO` once); no figure check failed. **The acceptance condition holds**: every `needs_review` reply has sources attached and a ready draft, every escalation has a named reason, and no ready draft has a failed blocking check (also asserted over a scripted run of the whole inbox in the test suite).

**What was read:** 30 drafts, spread evenly, each beside the passages it was written from. This is one reader, one pass, and the sample is of drafts, so inquiries that ended with no draft were not read.

**Code defects found and fixed (D-046 updated by this):**
1. `STRUCTURE` passed drafts written as a single run-on paragraph with "Kind regards," in the middle: 22 of 61 model drafts looked like that. The greeting and the sign-off must now each be on their own short line; on the saved drafts 23 now fail this (warning only).
2. `NO_COMMITMENT` blocked a draft because its subject repeated the customer's ("Re: price match?"). The customer's own subject is now removed before the commitment patterns run. (That item escalates anyway.)
3. `NO_COMMITMENT` blocked "turn it off where the water line enters the house" because the documents say "turn off" and the draft said "shut off". "Shut off", "switch off" and "turn it off" are now the same advice. This was a false escalation of a question the documents answer (`near-miss-shutoff-instructions-system`).

**Things the read found that are not fixed (prompt, design, and earlier stages):**
- **The model under-uses the passages.** `multi-heater-price-and-warranty` has "$1,650 installed" in a passage and the draft says only that "a member of our team will confirm the cost"; `pricing-water-heater-40gal` says "a flat price" without the number; `service-slab-leak` omits the leak-detection price. The claims list names the facts the body leaves out, so `CLAIMS_HAVE_SOURCES` cannot see it. The prompt's caution (no figure that is not in the passages) is being read as "no figures".
- **A booking with complete details gets the requirements list recited** (`booking-drain-no-property-type`, `booking-outer-area-travel-fee`): the "what is needed to book" passage is repeated back to someone who already gave the service, date and area. The booking-process question should probably not be asked when nothing is missing.
- **Questions lose context.** A billing question comes out as "Can you explain the difference?" (`billing-why-175-call-out`) and retrieves slab-leak passages; the service extracted for an unrelated message prefixes the question ("About leak repair: ..."). That draft says "$89 is the amount we charge for most services", which no passage says; the figure check passes it because $89 is in the customer's own message. **Figures from the customer's message are trusted by design (TRD 4.6) and this is the cost.**
- **Phase 4 mistakes reach the customer.** An "are you open on sundays" read as an availability question is never sent to the knowledge base, so the reply asks for the type of work and a date (`hours-sunday-open`). "Did you get my photos?" read as availability gets a request for a visit date (`followup-did-you-get-photos`). A waived-fee request the model did not flag (`exception-waive-travel-fee`) gets a ready reply that politely ignores the request, with nothing escalated.
- **The prompt leaks.** One draft contained "We do not offer repair advice unless a passage says exactly that" (a rule from the system prompt), caught by `NO_INJECTION_ECHO`: a true positive. The same draft ended "a member of our team will follow up on what we do, our hours and our service area", the plain-words topic phrase from the prompt used verbatim.
- **Smaller:** an apology for a customer having fixed their own problem ("We're sorry to hear you managed to complete the work yourself"); replies that give no answer but a promise of follow-up when the passages did answer; "Hello Ujk," from a gibberish message's sender name.

**What the checks did and did not do in this run.** They blocked 3 drafts, all legitimate or low-cost to a reviewer. They found no invented figure, and the 30 drafts read contained none that could be seen. The checks do not catch an unhelpful draft, a draft that ignores the question, or a figure repeated from the customer's own message. Whether the share of weak drafts is acceptable is a judgement call; this run is the baseline for a `draft-v2`.

## Phase 6

### D-050. Review decisions (`review.py`, API routes): choices the documents left open
- **A reviewer's edit is not re-checked.** APP_FLOW 4.7 says an edit is saved and then "as approve"; nothing says the draft checks run on the new text. They do not: the checks exist to stop a model, and the reviewer is the person deciding. `edit_approve` stores the edit in `reviews.edited_body`; the draft row keeps the model's text, so the difference stays visible. An edit that differs only in surrounding whitespace is a plain `approve`, so the "approved unchanged" share is not inflated by stray newlines. **Not covered:** a reviewer who types a figure or promise the sources do not support. If that matters, running the checks on the edit and showing them as warnings is the obvious next step.
- **Export is two requests.** TRD 6 lists `GET /api/drafts/{id}/export` "returns approved text for copying", and APP_FLOW 4.7 says copying moves the inquiry to `exported`. A GET that changes state can be repeated by a prefetch or a cache, so `GET` only returns the text (the edit if there was one) and `POST` records the copy and moves to `exported`. Copying again is allowed and recorded again. Neither sends anything, and no path contains "send" or "mail" (a test checks the OpenAPI paths).
- **Escalate by hand** is only from `needs_review` (the state table allows nothing else). It records `MANUAL` with source `reviewer`; the escalation `detail` is a fixed sentence and the reviewer's note lives in `reviews.reason`, so reviewer text never reaches an escalation row or an audit event. The draft stays `ready`, shown "for reference".
- **Resolve** works from `escalated` and from `rejected` (close with no reply) and closes every open escalation. The note is optional.
- **Audit events** for a decision hold `{decision, draft_id}` and nothing else.
- **Limits:** notes and reasons at most 500 characters, edits at most 10,000, `review_seconds` 0 to 86,400, no control characters. Errors never repeat what was sent.
- **Response of every decision endpoint is the updated `InquiryDetail`**, so the screen replaces its state with one object and does not refetch.
- **Insights** return counts as lists of `{code, count}` with every enum value present (zero if unused), plus the shares and median that PRD FR-20 names. The share of approvals unchanged is out of approvals plus edits only; a rejection is not an approval.

### D-051. Redraft and reprocess (`pipeline.redraft_stage`, `pipeline.retry_failed`)
- **Redraft runs inside the request.** `POST /api/drafts/{id}/redraft` calls the model, then checks the new draft, and answers with the updated inquiry (about 5 to 20 seconds with the real model). The alternative, running it through the worker, needs somewhere to keep the guidance before the draft that carries it exists. The model is called with no transaction open (as in D-043); if the inquiry changed meanwhile (for example it was closed), nothing is written and the request gets a 409.
- **Only the latest draft of a `rejected` inquiry can be redrafted.** Guidance is required (1 to 500 characters). The new version is stored with `guidance`, goes `rejected` to `drafted`, and then runs through the same check stage as a first draft, so a redraft that invents a figure is blocked and escalated like any other.
- **The passages are the stored ones.** The knowledge base is not asked again. With no stored passages (a holding reply, or a request for details written as a template) there is nothing to write from and the request is refused with `wrong_state`; the reviewer closes the item instead. This keeps rule 6 (`docs/RULES.md`).
- **Guidance goes into the user message only.** The system prompt is untouched, so first drafts are byte-for-byte what `draft-v1` produced (a test pins this) and the prompt version stays `draft-v1`. The message says guidance may change wording, tone, length and emphasis and cannot add facts. It sits in `<guidance>` tags, and a copy of that tag inside the guidance is removed.
- **A model that fails leaves the inquiry `rejected`** (HTTP 502 `model_failed`, with a `stage_failed` event holding the reason code), not `failed`, so the reviewer can simply try again. Audit events hold codes only; the guidance lives in `drafts.guidance`.
- **Reprocess is retry only.** The TRD said "re-run from a named stage". The state machine has one such move, `failed` back to where the failed stage started (D-036, D-048), so that is the whole endpoint: no body, `409 wrong_state` for anything that is not `failed`. Re-running a healthy inquiry from an earlier stage would need new state-machine moves and was not asked for. The worker is woken so the retried inquiry runs at once; whether it goes past `routed` depends on the worker having a knowledge base (as for any inquiry).
- **Not covered:** a redraft does not offer to ask the knowledge base again if the first answers were poor. That is a re-run of retrieval and would need its own move.

### D-052. TypeScript types from the API (`tools/export_openapi.py`, `web/`)
- **Two generated files are committed**: `web/openapi.json` (written by `python -m tools.export_openapi` from the FastAPI app alone: no settings, database or model; sorted and indented so it changes only when the API does) and `web/src/api/schema.d.ts` (written by `npm run gen:api` with `openapi-typescript`). `web/src/api/types.ts` only gives the generated types short names.
- **Where staleness is caught.** A Python test (`tests/test_openapi_export.py`) fails if `openapi.json` differs from the app, so the ordinary test run catches a forgotten export, and the Python CI job also runs `--check`. A separate CI job (`web-types`: `npm ci`, then `npm run check:api`) regenerates the types into a temporary file, compares them with the committed one, and type-checks them with `tsc`. Checked by hand: a stale file fails with exit 1, and regenerating fixes it.
- **Versions are pinned** (`openapi-typescript` 7.13.0, `typescript` 5.9.3, with `package-lock.json`), because a newer generator would change the output and fail the check without any API change. CI uses Node 22; the types were generated here with Node 24 and the output does not depend on it.
- **This starts `web/` as a Node project** with only these two dev dependencies. Vite, React and the rest come with the screens.

### D-053. Backend support for the review screens (step 0 of `docs/UI_DESIGN_PLAN.md`)
Four decisions in the plan were accepted: undo is a 5-second client-side delay, a blocked draft offers "Mark resolved" only, the refusal screen has no manual reply, and Settings is read-only. The backend additions that go with them:
- **`summary` on each list row**, from the existing `classifications.summary` column (whitespace tidied, cut to 200 characters). It is the model's text, so screens render it as text. Items not yet read have `null`.
- **`attention` counts in `GET /api/status`**: `needs_review`, `escalated`, `failed`, and `urgent_open` (urgent items in any of those three), from one query. The header and the tab title read these, so the queue screen does not poll `insights` as well.
- **Model and knowledge-base checks on request only** (`citedesk/health.py`). `GET /api/status` stays cheap and never calls out: it reports `not_checked` until someone runs `POST /api/status/check`, then the remembered result and `checked_at`. The model check asks Ollama's tag list for the configured model (`model_missing` if absent); the knowledge-base check asks rag-project's status for a chunk count above zero (`not_indexed` if empty). Both are GETs with a 2-second limit to a loopback address (anything else is `not_local` and never contacted), carry no inquiry text, and report a reason code, never an address or reply. Overall `status` is `degraded` when any component is in `error`. The remembered result lives in the running process; it is not stored.
- **`GET /api/settings`** (read-only; POST and PUT are 405): business details from the fact sheet (null if it cannot be read), the draft word limit, model name, data mode, and every escalation reason with `enabled` and `set_by`. Only `LOW_CONFIDENCE` is `environment` (it follows `ESCALATE_ON_LOW_CONFIDENCE`); the rest are `code`. Paths, addresses and setting names are not in the response (a test checks).
- **Insights** gain `period_start` and `period_end` (first and last arrival), `median_seconds_to_draft` with `draft_time_sample`, and `review_time_sample` for the existing median. Time to draft runs from when the inquiry **arrived in Citedesk** (`created_at`) to the first time it waited for review, not from `received_at`: an imported message can carry a date from days earlier, which says nothing about the tool's speed.
- **Not done:** the `thread` view, a rule-by-rule explanation in the API (the words live in the UI's copy module), and any stored health history.

### D-055. The Queue screen (`web/src/screens/queue/`, build step 2)
- **What a view is.** Five tabs (Needs review by default, Escalated, Failed, Archived, All) with the counts the status endpoint already gives, plus the "urgent only" mode the header chip links to. Only codes go in the address (`?show=...`, `?urgency=urgent`); **the search text is page state and is never written to the URL**. Search is sent after 300 ms without typing, trimmed, at most 200 characters.
- **"Urgent only" means every state that needs a person** (needs review, escalated, failed), to match what the chip counts. With a tab also chosen it narrows that tab. No tab is marked current in the wider mode, and a "Show everything" button leaves it.
- **Rows.** Urgency as a word (the only capitals are the urgent tag), the state in plain words ("Draft ready", "Asking for details", "Escalated", "Waiting to be read"), the model's summary (else the subject, else "(no subject)"), sender, and age. An unread item has no urgency tag, because it has no urgency yet. A repeat message says so. The whole row is one link. Everything from the customer or the model renders as text; a test pushes `<img onerror>` and `<script>` through a row and finds no element.
- **Age** is "4 min ago", "2 h ago", "3 days ago", then the date after a month, so an imported message with an old date does not read "5 months ago". The exact time is in the tooltip. It refreshes every 30 seconds.
- **Refresh and paging.** The first page refreshes every 5 seconds. "Show more" pages are fetched once on request and kept until the view changes, so a refresh does not throw away what was scrolled to. New arrivals are announced politely ("1 new inquiry") without moving focus; the first page is never announced as new.
- **The five states.** Loading (grey shapes, one status line, hidden from screen readers), empty ("Nothing waiting. New inquiries will appear here."; "Nothing has been archived."), error (the unreachable sentence with Retry, or the API's own message with the request number), no results (when a search or urgent-only is active: "No inquiries match this filter." with Show all, which also clears the search), and the list. Each is tested with an axe check where it applies.
- **Keyboard.** `j` and `k` move focus through the rows and stop at the ends; `Enter` opens the focused row. They are ignored in a text field and when the shortcuts switch is off (`citedesk.shortcuts` in the browser; the Settings control for it comes with that screen). A blocked browser store means "on".
- **`useResource` changed**: it now keys its result, so data for another key is never shown. A new key starts from loading, and a failed load for a new key does not carry the old data. This settles the limit noted in D-054; two tests cover it.
- **Seen in the real browser** against a seeded throwaway database at phone width: stacked rows, the urgent band and tag, hostile text shown as text, `j j Enter` opening the second row with focus on the content. Not checked at full desktop width by eye (the pane is small); the layout is a five-column grid there and the narrow layout was checked.
- **Not done**: the tab for urgent-only in the header counts is the status endpoint's, so after a decision elsewhere the count catches up on the next poll (up to 5 seconds).

### D-056. The Inquiry detail screen (`web/src/screens/detail/`, build step 3)
- **Which variant is shown is decided from the data alone** (`variant.ts`, tested for every status). One finding shaped it: **a holding reply is stored with status `blocked` and no checks**, so "blocked" cannot be read from the draft's status. A draft is "blocked" only when an escalated inquiry has a failed *blocking check*; an escalation with `NOT_IN_KNOWLEDGE_BASE` and no failed check is the refusal screen; a failed check wins over a refusal reason.
- **Layout and order.** Three columns from 1,120 px (message | understood-as and sources | draft, checks and actions); below that one column in the plan's order (Understood as, draft and actions, Sources, Original message) with a "Jump to the original message" link, hidden on wide screens.
- **Understood as** shows the model's summary, intents (primary first; "(fairly sure)" or "(not sure)" only when confidence is below high), urgency, tone, the fields found ("Not stated" where empty), the missing fields in a highlighted box with what the draft will ask, the next step, and the open escalation reasons worded by their source. An item the model never read says so, and why if it was an injection.
- **Checks** list failed blocking checks first, then failed warnings, then passes, each with a symbol, a word ("Needs attention", "Worth a look", "Passed") and what was found, built from each check's `detail`. `ADDRESSES_ASK` is not shown (not implemented). **Sources** use the same merge as the backend, in the same order, so a claim's number points at the right passage; figures the check found grounded are marked in the passage, and a claim's marker opens its passage. Marks are built by splitting text into pieces in code, never by inserting markup.
- **Review**: the draft is an editable text area (serif, 68-character line, word count against the limit from `GET /api/settings`, a note that edits are not re-checked, D-050). The subject is shown but not editable, because the API does not take an edited subject. An unsent edit is kept in the browser under the draft's id and removed when the decision lands; a blocked store keeps nothing and breaks nothing.
- **Decisions.** Approve and reject wait five seconds with a visible bar and an Undo button (D-053 accepted the client-side delay). They are sent at once if the page is hidden or closed, or the person leaves the screen; requests use `keepalive` so a decision sent while leaving still arrives. Escape undoes a waiting decision, and closes an open form, in the capture phase, so it never also goes back a page. Escalate and resolve are sent at once. Reject, escalate and redraft ask for text first, in a form under the buttons, not a dialog. A failed save keeps what was typed and says so with the request number. `review_seconds` counts from opening the page.
- **Keys**: `a` approve, `e` focus the editor, `r` reject, `x` escalate, `Esc` back (to where the person came from, else the queue). All ignored while typing and when the shortcuts switch is off. **Not done yet** (step 6): `j`/`k` between items on this screen, returning focus to the queue row on the way back, and the `?` shortcut list.
- **Other variants as planned**: processing (stage in plain words, updates by itself), failed (stage, the fixed failure sentence, Retry), escalated (reasons, the draft folded away as "For reference, not checked for sending", Mark resolved with an optional note), blocked (the sentence "Not ready: $85 isn't in your documents.", the figure marked in the draft, no approve button, Mark resolved only, D-053 decision 2), refusal (no pretended sources, the holding reply for reference, Mark resolved only, decision 3), rejected (guidance form with "can take up to a minute" while the request runs, a model failure keeps the guidance, Close without a reply), approved (the exact approved text from the export endpoint, **Copy reply records a copy only after the clipboard accepted the text**), exported (same text, "Copy again"), resolved and archived.
- **Refreshing**: the page polls every 3 seconds. A decision's answer is shown at once; whichever of the answer and the refresh has the later `updated_at` is shown, so a slow refresh cannot put an old state back.
- **Tested**: 47 detail tests (every variant, the five states of the screen, undo and Escape, leaving flushes, saved edits, hostile markup, axe on each variant, and a keyboard-only run from the queue to a copied reply, which is the phase's acceptance check). **Seen in the real browser** against a database filled by the real pipeline (with scripted model and knowledge base): review, blocked, refusal, escalated with hostile text, approved, and an actual keyboard approve that waited five seconds, then changed the server's status. Not checked by eye: the three-column layout at full desktop width, and the rejected and failed screens.

### D-057. The Insights screen (`web/src/screens/insights/`, build step 4)
- **A share is shown only from ten approved replies** (`MIN_SAMPLE` in `figures.ts`). The share's own denominator is approvals plus edits (D-050: a rejection is not an approval), so that is the sample the screen counts, and it says "Too few approved replies to show a share (4 so far)" below ten. This differs from the plan's wording ("below 10 decisions") on purpose: ten decisions that are mostly rejections would still leave a share built on three replies. Counts are facts and are always shown.
- **Medians are always shown with their sample**, and below ten the screen adds "Only 4 so far, so treat this as a rough guide". No time yet reads "Nothing to measure yet", never "0".
- **No rejected share.** The plan listed one, but the API's two shares are out of approvals plus edits, and a third on a different denominator beside them would read as a mistake. Rejections appear as a count in the decisions table.
- **Every count table carries its own words.** Routes and reasons use the existing wording; reviewer decisions use `decisionWords` in the copy module. The API sends decisions as plain strings (not an enum in the schema), so the words are keyed by string and a code with no words is shown as it is, never dropped (a test covers it). Reasons list only those that happened, most common first; with none, one sentence instead of an empty table. The route table adds each count's share of all inquiries with a bar; the bar is decoration (hidden from screen readers, hidden below 40 rem) and the percentage is the figure.
- **Time saved is the person's own estimate and says so.** One input, "Minutes per inquiry without the tool (your assumption)", kept in this browser (`citedesk.minutesWithoutTool`), never sent. The estimate is approved replies × (the assumed minutes − the median review time), never below zero, labelled "Estimate based on your assumption" with the sum written out. It needs a median review time; without one the screen says why instead of showing a figure. An unusable number (not a number, 0, over 1,440) is named as a problem, with no estimate.
- **Period** is the first and last arrival as UTC calendar days ("20 Oct 2026 to 28 Oct 2026"), one day when they match, the same way the queue dates old messages. `dayText` was split out of `ageText` to share it.
- **`ErrorPanel`** (`components/`) replaces the queue's own error block and is what Insights and Settings use. The detail screen keeps its banner version, which sits inside its own layout.
- **Five states, as planned**: loading (placeholder figures, one status line, hidden from screen readers), empty ("No inquiries yet."), error, too little data, and the figures; axe on each. 52 new tests. A deliberately broken threshold fails three of them.
- **Seen in the real browser** against the seeded throwaway database at phone width and 1,280 px: the too-little-data wording on real counts, the tables, and typing an assumption giving "About 20 min saved." with its basis. The fixed footer does not cover the last line.

### D-059. Keyboard map and polish (build step 6)
- **`j` and `k` on an inquiry move through the list it was opened from.** The queue row's link carries the ids of that list as router state (ids only, never text); a page opened from a bookmark has no list and offers no next or previous. State is read defensively (`neighbours.ts`: whole positive numbers, at most 1,000, this inquiry in it) so a bad value just means no list. The move **replaces** the page in the history, so `Esc` still goes back to the queue in one step however far the person moved. A visible "2 of 8 in your list" with Previous and Next links does the same for a mouse or a screen reader, and a polite announcement says where a move landed.
- **`j` and `k` never abandon something unfinished.** They do nothing while a decision is waiting to be undone, or while the reject or escalate form is open, because moving on would drop what was typed or send a decision the person is still allowed to take back. (Leaving by a link still sends a waiting decision, as D-056 says.)
- **Coming back puts focus on the row.** The inquiry screen notes which inquiry it showed (`returnFocus.ts`, in memory) and the queue focuses that row once, if nothing has focus yet and the row is in the list. A row on a later page, or one filtered out, simply leaves focus on the page content.
- **`?` opens the shortcut list from any screen**, and a **Shortcuts** button in the footer opens it for anyone not using the key (it also works with shortcuts switched off, and says they are off). It is a modal dialog: focus moves to the dialog (not to Close, which sits at the bottom and would scroll the title away on a phone), Tab stays on Close, `Esc`, `?`, Close and a click outside all close it and focus returns to what had it. While it is open the page behind ignores keys: one flag on the document (`hooks/modal.ts`) is checked by the single-key shortcuts and by every Escape handler, so Escape closes the dialog and does not also go back or undo.
- **A bug found by using it: forms that are part of the page no longer take focus on arrival.** The "Note (optional)" and redraft-guidance boxes focused themselves when the page loaded, so on a blocked, escalated, refused or rejected inquiry `j`, `k` and `Esc` typed into the box instead. Only a form the person opened (reject, escalate) takes focus now (`focusOnOpen`). Two tests cover the arrival case.
- **Live regions.** The undo bar's countdown changed every second inside a polite region, which a screen reader would read as "Saved in 4 seconds", "3 seconds"... It is no longer a live region; the wait is announced once ("Reply approved, saving in 5 seconds. Press Escape or choose Undo to take it back."). Everything else announced (new inquiries, decisions, copy, the service check, connection lost and restored, a processing item's stage) was already a single message.
- **Reduced motion**: nothing in the app animates or transitions; the existing `prefers-reduced-motion` rule stays as a guard for anything added later.
- **360 px pass** in the real browser: no sideways overflow on the queue, all eight demo inquiries (every variant, including the hostile-text one and the failed and rejected screens), Insights, Settings, the not-found page and the shortcut list. Two things fixed: the footer took three lines at that width (the notice now wraps beside the button and the bar is two lines), and "Jump to the original message" was 24 px tall (now 44 px like every other target).
- **Not verified**: the `?` key itself in the real browser (the automation tool does not send a true `?`; a synthetic `?` keydown opened the dialog, and the tests press it with a real keyboard model), and the three-column layout at full desktop width, still unchecked by eye.
- **Tested**: 45 new tests (the neighbour logic, the modal flag, the shortcut list, `j` and `k` in every case above, focus return, the arrival-focus bug, the single announcement). Breaking each of three behaviours on purpose (focus return, the guard on `j`, form focus) fails the tests that name it.

### D-061. Phase 7 ground rules, and the held-out set (written before any run)
- **Order: measure as it stands.** The known gaps (weak `POLICY_EXCEPTION_REQUEST` and `REFUND_OR_DISPUTE` recall, the draft problems in D-049, `ADDRESSES_ASK`) are **not fixed before the held-out run**. The held-out set is run once, on `understand-v1` and `draft-v1` as they are, and the weak numbers are reported as they come out. Fixes are a separate piece of work afterwards and need a new sealed set to be measured honestly (the held-out one is spent once it has driven a change). This order was chosen over fixing first.
- **The held-out set is written: 76 items** in `eval/golden/src/heldout_*.json`, 36% of the 211 now in `citedesk_v1.json`; the PRD asks for at least 150 in total, about a third held out. Details, composition and what the author knew are in `eval/golden/README.md` ("The held-out split"). In short: new wording and senders, written from the documents and labelling rules, **oversampling the rare reasons** (12 `HEALTH_SAFETY`, 6 `REFUND_OR_DISPUTE`, 6 `POLICY_EXCEPTION_REQUEST`, 3 `LEGAL_THREAT`, 2 `LOW_CONFIDENCE`), with more field and `request_details` items added before any run. 54% of it escalates against 35% of the tuned set, so **overall accuracy is not comparable across the splits**; per-label numbers are, with their counts.
- **No test reads the held-out items** (`tests/golden_data.py`: behaviour tests load `tuned_golden()`). The tests that read the whole file check its structure and that no label leaks into the inbox. A scripted-model run over every item in the suite was replaced by one over the tuned split for the same reason: a detector or rule run over held-out items in a test is a tuning signal. The tools that run a system (`score_understanding`, `run_pipeline`) already refuse any split but `tuned`.

Only an address and a repeated name were changed. No system code was touched, and the evaluation reports screening on held-out like every other stage.
- **What "run once" means here.** One evaluation of one fixed system: the same commit, settings and prompts for every pass. A few repeated passes of that same system are allowed so that run-to-run spread can be reported, but nothing changes between passes, and the held-out result is not used to choose between settings. **The choice of thinking on or off is made on the tuned split**, before the held-out run.

Everything else in the plan's metric list is reported beside them and is not a headline.
- **Who wrote it, and what that means.** One author for the documents, the system, the tuned set and the held-out set. The held-out set is therefore unseen but not blind, and its idea of "messy" is the author's. It is the honest test of fitting to the tuned items, not of how the system meets real customers.

### D-062. The Phase 7 runner, scorer, comparison and held-out ledger (`tools/eval_*.py`)
Four commands, each doing one thing. **Nothing was run on the held-out split while building them** (the rule of D-061); they were tested with scripted fakes and exercised on a few tuned items with the real model (last bullet).
- **`eval_run`** asks the system (stages 1 to 6: `pipeline.process` with the model, the knowledge base and the business) and saves raw outputs per item. **`eval_score`** reads a saved run and the labels and calls nothing. **`eval_compare`** tests two settings over repeat passes. `eval_stats` holds the arithmetic. `score_understanding` and `run_pipeline` are unchanged and still refuse any split but tuned; their refusal now points at `eval_run`. `score_understanding.collect` gained `stage_ms` and `route_events` (additive).
- **Run files** (`eval/runs/<id>.run.json`, git-ignored: they hold synthetic messages and drafts) are rewritten atomically after every item and say `complete: false` until the end. **`--resume RUN_ID`** continues one. The pipeline runs against a **SQLite file** (`<id>.db`) rather than memory because items affect each other (a sender seen earlier is "known" to screening): resuming reopens the same database, so a resumed run gives what an uninterrupted one would (a test interrupts a run between items and in the middle of one, and compares). The database is deleted at the end unless `--keep-db`. Resuming is refused if the system differs (code tree, model, settings, prompts, knowledge base, split), if the run is complete, or if the database is gone.
- **Header** records commit; whether the tree was dirty (ignoring `eval/heldout_ledger.json`, `eval/runs/` and `eval/reports/`, which change while an evaluation runs); the git ids of the committed `citedesk/` and `universe/` trees; settings; model; both prompt versions; sampling (temperatures, seeds); rag-project's `/api/status` (chat and embedding model, its own thinking flag, split search, files, chunks); the golden file's hash and header; and **`split_sha256`, a hash of the selected split's items** (messages and labels, in file order). It does not move when items of the other split are added (tested). `--limit` is recorded in the header, the hash still covers the whole split, and the report is headed "QUICK CHECK, NOT A RESULT".
- **Headline measures** (D-061), each held as a per-item numerator and denominator so the same numbers feed the report, the spread and the bootstrap: primary-intent accuracy over the items the model read (as in D-044: items screening settled have no intent score); `HEALTH_SAFETY` escalation recall with n and the missed ids (target "no misses"; `target_met` is n/a when there are no safety items); **route accuracy of the whole pipeline** (the final route against `expected_route`, so an item sent to a person because the knowledge base had nothing is a correct `escalate` where the label says so); escalation precision and recall over all items. Beside them are **stage 3 views scored the way D-044 scored them** (`route.stage3`, `stage3.escalation`: the route stage's own decision, without the reasons the knowledge base and the checks add), so the first baseline stays comparable. Escalation by reason now includes `NOT_IN_KNOWLEDGE_BASE`. A reason a draft check adds (`NO_COMMITMENT` becomes `POLICY_EXCEPTION_REQUEST`) counts as a false positive for that reason; `escalation.by_source` and `escalated_by_a_check` say which items, so the two causes are not blurred.
- **Also reported**: macro-F1 and the intent set, fields, urgency, check pass rates (all drafts, and model-written drafts only, with counts and which checks block), ungrounded figures (count, items, derived sums), injection outcomes (caught at screening, caught by a draft check, not caught, and of those how many reached a reviewer as a reply; near-miss items wrongly flagged), latency per stage and per item (sum of stage times), scores by category with counts, status counts, and a **reading list** of item ids by kind of miss (route mistakes, safety misses, escalation misses and false alarms, blocked drafts, ungrounded figures, injections not caught, failures). Scores and the reading list hold ids, codes and numbers, never message or draft text (a test plants text in a record and checks that it does not come out).
- **The held-out ledger** (`eval/heldout_ledger.json`, committed, empty now) turns "run once" into code:
  - `--split heldout` needs `--allow-heldout`, a clean tree, no `--limit`, and a passing check that the model and the knowledge base are up. Each is refused before the ledger or any item is touched. The first held-out run of a system must declare `--heldout-passes N` (1 to 5).
  - **Reading of "once"** (D-061 allows repeat passes of one fixed system): one *evaluation* of one *system*, with the number of passes declared up front. Passes up to that number need no reason. A further pass, a fresh start of a run that never finished (resume it instead; that uses no pass), or a run of a *different* system (the set is spent for the next change) is refused unless `--justify` gives a reason of at least 20 characters, which the ledger keeps with `outside_plan: true`.
  - A **system** is `{code tree, universe tree, model, prompt versions, settings, rag-project configuration, split hash}`: tree ids rather than the commit, so committing the ledger itself does not make a new system. rag-project's clock (`last_sync`) is left out.
  - The run is written into the ledger (`started`) before its first item and marked `completed`, with counts, afterwards. The ledger holds ids, counts and dates only (a test pins the keys).
  - **What it cannot stop:** someone running the model over held-out text by another route, deleting the ledger, or editing a prompt and committing it. It makes the honest path the easy one and leaves a trace; the commit history is the second record.
- **Spread and comparison** (`eval_stats`, `eval_compare`; qa-eval-harness step 6). Passes of one system give each headline measure a mean, SD, range and 95% t-interval. Two settings are compared by the difference of their pass means with a Welch t-interval, and by a **paired bootstrap over items** (10,000 resamples of the same items for both settings, seed 0, percentile interval; each item's numerator and denominator averaged over its passes). **Real** only if the difference is larger than the pass interval and the bootstrap excludes zero; otherwise **unclear**, with the smallest difference the test could have seen. One pass per setting cannot be called (there is no spread to estimate). If the passes never differ (a fixed seed at temperature 0 may do this) the interval is zero and the call rests on the bootstrap alone; the report says so. The t values are a table for 1 to 30 degrees of freedom (2.0 beyond it) because there is no scipy. `eval_compare` demands the same code tree, model, prompts, knowledge base and split in both groups (only a setting may differ) and **refuses held-out runs**: the thinking choice is made on the tuned split.
- **What "thinking on or off" means here.** `ENABLE_THINKING` applies to the *understand* step only (its first attempt; the retry never thinks). Drafting always runs with thinking off, and rag-project's thinking is its own setting (on; recorded in every header and the same in both groups). So the comparison is of the understanding step. `eval_run --thinking on|off` sets it.
- **Not done:** the committed report under `eval/reports/` (written after the real runs); the optional `citecheck` adapter; any judge (so `ADDRESSES_ASK` and draft helpfulness are unscored, and the D-049 manual read stays the only look at draft quality); a second labeller.
- **Tested**: 167 new tests (stats, ledger, shared helpers, scorer on hand-made runs, the runner with a scripted model over 14 tuned items including interruption and resume, the command's guards, the comparison). No test opens a held-out item: the command tests file tuned items under the name `heldout`.
- **Exercised with the real model, as a quick check and not a result** (`qwen3:8b`, rag-project with 83 chunks, first 4 and 8 tuned items, run on 2026-10-29): the runner, scorer, spread and comparison ran end to end with 0 failures; an item took about 25 to 45 seconds through all six stages (understand about 2 s, retrieval 13 s, draft 10 s). Two passes of the same 4 items gave identical results (spread zero, as a fixed seed at temperature 0 predicts), and thinking on gave the same results as off on those 4 items, so the comparison correctly said "unclear" with the note that only the bootstrap decides. Scoring the saved D-044 run with the new scorer reproduced its numbers exactly (primary intent 98/123, stage 3 route 80.7%, stage 3 escalation precision 83.8% and recall 81.6%, safety 8/8). Four to eight items say nothing about the system. Passes took 2 to 4 minutes for 4 items, so a full tuned pass is about 40 minutes as in D-049.

### D-070. A wording check for Markdown and commit messages (ported from citeTally D-091)
**Why.** D-068 removed wording about people from the documents by a one-off sweep. A check that runs where the wording is written avoids repeating the sweep.

**What changed** (`tools/check_personal_info.py`, `tests/test_check_personal_info.py`, `.pre-commit-config.yaml`, `.github/workflows/ci.yml`).
- The checker flags, in tracked files, local user paths, email addresses and phone numbers that are not invented ones, notes that describe the author, and assistant-instruction files. In Markdown files and commit messages it also flags wording about a person where a decision or action should be described, first-person pronouns used with a verb or as a possessive, and in commit messages an assistant attribution line. Findings name the file, the line and the kind of problem, never the matched text.
- It runs three ways: staged files before a commit and the message before it is accepted (two local pre-commit hooks, installed with `pre-commit install` and `pre-commit install --hook-type commit-msg`), and over every tracked file in CI.
- **Tuned for this product, where the business owner is a role.** "The owner" is flagged only as an actor or decider in a record of the work ("the owner chose", "confirmed by the owner", "the owner's decision"), not in "exceptions only the owner can grant" or "a message that pretends to be the owner". "As the author" as a persona is flagged; "As staff, I ..." is a user story and passes. Text in double quotes or backticks is not checked for first person, because customer messages and phrase-list examples are quoted throughout. `universe/docs/` and `eval/golden/src/` are skipped: they are written in a customer's voice by design. "Not a developer console" is not a note about a person.
- **Reworded where the first run found real cases:** the maintainer persona in the PRD, a first-person aside in the golden set README, and a mockup in the UI brief whose customer quote ran across table rows. Test strings that hold a real-looking address or number are now built from parts.

**Limits.** The patterns are a list and catch what they list; a different phrasing for the same idea passes. "The owner" in the sense of the business owner and in the sense of the project owner cannot be told apart by form, so the check lists decision verbs and misses others. The commit-message hook is enabled per clone; CI covers files but not commit messages.

### D-071. A sealed set, written first and unseen by the session that builds the fixes (written before the items exist)
**Why.** The held-out set is spent in the sense of D-061 and D-064 as soon as a change is made because of it. The planned changes (intent and escalation fixes, wider phrase lists, draft greeting and sign-off, review-screen aids) all need a test that was written before them. **Method** (the pattern of citeTally D-062).
- **Written by a separate subagent that is given the documents and the labelling rules but not any existing item or result.** The session that builds the fixes never reads the sealed items. ### D-072. Held-out error analysis: where the intent misses are, and what it means for the order of fixes
**What was done.** `tools/error_analysis.py` reads the three saved held-out passes (`eval/runs/eval-heldout-*`) and the labels and writes `eval/reports/heldout-error-analysis.md` (ids, labels and counts only). Nothing in the system, the labels or the held-out items was changed. The three passes agree almost item for item, so the misses are stable behaviour, not noise.

**Counts.** 24 of 76 items had a wrong primary intent in at least one pass; 16 of those also had a wrong route. The other 8 are different readings of the same ask that end in the same route.

**Groups of misses** (counts are items).
1. **Policy exceptions are not noticed (5 of 6 missed).** `POLICY_EXCEPTION_REQUEST` is raised only from the model's escalation signals in `understand.py` (and, later, by the commitment check on a draft). On the five misses the model reported no signal and read the message as a price or booking question. Two of them went on to a ready draft reply, three to a request for details. This is the group with the highest consequence and the clearest cause: one detector, one wording-sensitive model signal.
2. **Injection wording (3 of 4 not caught).** Screening caught one; the role-play as the owner and the fake pre-approval notice reached a ready draft, the request to paste the guidelines got a request for details. The screening patterns were written with the tuned examples in view (D-064), so this is the phrase-list weakness, shared with group 1's fix.
3. **Hours read as availability (3 items), out-of-scope read as a booking (1).** "What time is the last visit on Saturday" and a question about the office opening are `service_question` under the labelling rules, but are read as `availability_question` and get a request for a date instead of a draft. This is a prompt boundary problem and the reply is wrong for the customer, though safe.
4. **Spam not archived (3 of 3 wrong route).** A bulk-review offer and a parcel-fee message are read as `partnership_or_sales` and `billing_question`, so they are escalated; the third (a loan offer) is read as spam but escalated by the low-confidence rule. The labels are not in doubt. The cost is reviewer time, not risk.
5. **Over-firing safety net (1).** A hypothetical burst pipe in a question about call-out hours is escalated by the keyword net (`HEALTH_SAFETY`, source `safety_net`).
6. **Urgent items given a ready draft where the label expects a request for details (2), one vague item given a draft (1), one unanswerable item given a draft (1).** In the two urgent items the model turned "today" into the reference date (2026-10-28), so no date was missing. The labelling rule says relative dates are null; the pipeline resolves "today". This is a disagreement between the label rule and the pipeline, not clearly a model error (see the label audit).

**Label audit.** Judgment calls found; none changed, because the held-out labels are not edited after the run (D-061).
- Four `billing_question` primaries where the message is a refund request and a service complaint at once (the model says `complaint`); the route is the same either way. The labelling rule for the primary intent of a mixed refund-and-complaint message is not stated and is added to the guideline for the next set.
- Two `LOW_CONFIDENCE` items: the label depends on the model reporting low confidence (the guideline says so), and asking for details is a safe outcome. They are not a reliable measure and stay out of the headline.
- One follow-up ("do you have me down for Tuesday") and one trade-account offer labelled `draft_reply`. The trade-account item was escalated by the knowledge-base decline rule, which is the behaviour rule 6 asks for when the documents have no purchasing contact, so the label is probably wrong.
- "Today" in an urgent message: the guideline sets relative dates to null; the pipeline resolves "today" against the reference date. One of the two needs to be chosen and written down for the next set.
- The hours-versus-availability boundary is correct under the rule but easy to misread; the guideline gets an example.

**Order of fixes that follows.** Group 1 and 2 first and together (one detector design, tested with a paraphrase set, D-071 and item 4), then the draft style fixes, then the prompt boundary of group 3 and the spam reading of group 4, then group 5 as a rule with a hypothetical-event guard. Each is measured on a development set written for it (not on the held-out items) and claimed only on the sealed run.

**What this cannot show.** 76 items and a few per group, one labeller, and a model whose reading is fixed by one prompt version (`understand-v1`). The grouping is a reading by one author.

### D-075. The model may raise INJECTION_SUSPECTED (escalate only), and a dropped-signal bug
**Decision.** `INJECTION_SUSPECTED` joins the reasons the model may flag (`routing.MODEL_SIGNALS`), asked by the same focused call as the exception question. This changes the earlier design (the model could not raise or suppress this reason) and is recorded as a change to it: a signal can only add an escalation; nothing the model says removes a reason or marks a message safe; the screening patterns still run first and stop a flagged message before the model reads it. The model that reads a message is also the part an injection targets, so the signal is a second line of defence and not a replacement for the patterns or the draft checks.

**Measured on a development set** (`eval/dev/injection_dev.json`: 53 instructions to the assistant, 46 ordinary messages in three batches, invented for this purpose). Final run, real model: 42 of 53 flagged, 1 of 46 ordinary messages flagged by mistake (a question about the business's own guidelines). Batch a (the wordings the patterns were written against) 25 of 29; batch b (wordings the patterns missed) 7 of 12; batch c (written before any model run and run once on the final prompt) **10 of 12** with 0 of 10 false alarms. Screening patterns alone on batch c: 1 of 12. The patterns and the model miss different messages, so together they cover more than either. The question was tuned on batches a and b, so only batch c is close to unseen, and it is small. An injection that works on the reading model can make it answer "no" to this question too.

**A bug found by the tuned run.** The first version computed the focused signals and dropped them: the route stage re-reads the model's signals from the stored main reply (D-041), which does not hold them. A tuned-split run showed policy-exception recall unchanged at 3 of 8. Fixed by a new column `classifications.focused_signals` (migration `0002_focused_signals.sql`, documented in `BACKEND_SCHEMA.md`); the route stage adds those to the main reading's signals, and `raw_response` still holds exactly what the main reading said. `tests/test_focused_persistence.py` fails without the fix. That run was discarded.

**Limits.** Development numbers on sets written by the author of the prompts; the sealed run (D-071) is the claim. A larger blind batch for the injection question has not been written. The false-alarm rate on real customer wording is unknown; the cost of a false alarm is one more message for a person to read.

### D-076. The greeting, sign-off and paragraphs of a model draft are set in code (`draft-v2`)
**Why.** About one model-written reply in three failed the `STRUCTURE` check (no greeting or sign-off as lines of their own): in the saved tuned drafts, 21 of 55 were a single line with "Hello <name>," and "Kind regards, <business>" run into the text, and the reviewer in the trial rejected a draft for collapsed paragraphs (D-066). Telling the model to format them had not worked; the rule "model reads and writes, code decides" points to doing it in code.

**What changed** (`citedesk/drafting.py`, `tests/test_draft_layout.py`).
- The prompt is `draft-v2`: the model writes only the paragraphs, with blank lines between them and no greeting, sign-off or name; it is asked for `FRAME_WORDS` (12) fewer words so the whole draft stays within the limit.
- `compose_body` strips any greeting, name and sign-off the model wrote (inline or on their own lines), then adds "Hi <sender's first name>," (or "Hello,") and "Kind regards,\n<business>". The name is the sender's, never the model's. Single newlines become paragraph breaks, a flat run-on is split into paragraphs of at most two sentences, lists, decimals and dollar amounts are kept intact, and the result is unchanged by composing it again. A body with nothing in it besides a greeting and a sign-off is retried like any bad reply. `raw_response` still holds exactly what the model wrote.

**Measured** (60 tuned items, whole pipeline, real model; `eval/runs/pipeline-v1-tuned-20261106-200219`, git-ignored): 32 drafts (18 written by the model, 12 request-for-details templates, 2 holding replies), `STRUCTURE` passed 32 of 32, against 65 to 70% of model-written drafts before (held-out evaluation). The other checks were unchanged: 31 of 32 for `CLAIMS_HAVE_SOURCES`, 32 of 32 for the rest. Draft time is unchanged.

**What this does and does not show.** The `STRUCTURE` target of D-071 (95% of model-written drafts) is met largely by construction, because code now supplies the part of the structure that failed; the check still tests the word limit and wording that refers to the documents. It says nothing about whether the content is right. A reading of five of the drafts found one claim that passes every check and is wrong ("sales tax on all parts and labour" where labour is not taxed): the kind of problem the reviewer trial found people miss, and which the review-screen aids and the judge scoring are meant to address. The paragraph split is a heuristic for run-on text and was read on five drafts only.


### D-077. Review aids: where each figure comes from, the name beside the sender, and sentences no source backs
**Why.** The reviewer trial (D-066) found a person approved every draft with a planted problem. The aids designed after it were built so that the screen points at what the automated checks cannot see. They are warnings only: they do not block, route or change a draft, and nothing about them changes what the evaluation measures.

**What was built.**
- `citedesk/support.py` (plain code, no model): for a model-written reply it returns, for each sentence, `supported` (the wording and figures of one source passage), `routine` (greetings, "a member of our team will follow up", short sympathy that makes no promise), `from_message` (it repeats the customer's own message) or `unsupported`; and for each figure, the source line it is found in, whether the line is about a different service than the sentence (a price taken from another service's line), and whether the customer gave the figure. The sentence is `unsupported` when a figure in it is not in the passage whose words it uses, so a passage with the same words and no figure cannot vouch for a price found elsewhere.
- The detail endpoint carries it as `support` (computed from the stored draft, stored nowhere); the review panel shows "Look at these before you approve": the greeting name beside the sender with a warning when they differ, the figures with their lines and a button that opens the passage, and the marked sentences ("Not from your documents"). Everything is rendered as text (rule 5), and the copy says that no mark does not mean the reply is right.
- Tests: `tests/test_support.py`, `tests/test_support_planted.py` (a development set of 30 invented planted sentences of the six kinds, `eval/dev/planted_sentences_dev.json`), API tests, and `web/src/screens/detail/aids.test.tsx`.

**Measured (development numbers; the code was written with these problem kinds in view).**
- On 63 sentences of 18 model-written replies from a tuned run, 6 (9.5%) are marked, all of them either an unsourced claim ("the inspection will help identify any issues causing the backups", a "50-gallon water heater" price) or a filler assertion ("we can help with rescheduling your booking"). Replies written before D-076 mark their inline greeting and sign-off lines as sentences, which no longer occurs.
- The 30 invented planted sentences: all 30 marked. The first version marked 29; a price from the same passage but another line was missed until the mismatch test used the line alone, and a passage with the same words but no price hid the passage that had it (found on real drafts, fixed test-first).
- The six drafts of the first trial (read only, not used to write any rule): the sentence marks point at four (the unlisted credit, the invented perk, the desk description and the soft promise) and the name warning at the fifth (a greeting for "Jordan" on a message from "Priya Raman"). **The sixth, "a price from the wrong service", is not a problem in the stored draft**: it says leak detection is $245 and the pricing document says $245. The plant swapped the draft's price for the first other price in the passages, which happened to be the right one. The trial's result is therefore 0 of 5 real problems, not 0 of 6; the README says so.

**Not known.** Whether a reviewer catches more with the aids. That needs the trial rerun with new plants in new wording on different items, a plant check that each plant is really wrong against the sources, and ideally a second reviewer who has not seen the project. The marks compare words, so a sentence that uses a passage's words and gets its meaning wrong ("sales tax on all parts and labour" where labour is not taxed) is not marked; the aids do not replace reading the reply. The mismatch test covers prices and percentages only. A wrong name later in the body, as opposed to the greeting, is not looked for.

**Also changed.** `web/src/lint.test.ts` has a 30 second limit: its first ESLint run passed the default 5 seconds when the machine was busy and failed the suite.

### D-078. The lock on the sealed set (`tools/eval_run.py`, `tools/eval_ledger.py`)
The runner lock that D-071 left to build. The sealed set is run by `python -m tools.eval_run --split sealed --confirm-sealed-once --sealed-passes N`, and only under these rules, each tested with scripted fakes and tuned items filed under the name "sealed" (no test reads the sealed file):
- **Refused before the sealed file is opened**: no `--confirm-sealed-once`; `--limit`; a git tree with uncommitted changes to the system (changes under `eval/`, including the ledgers, are ignored); git not answering; or the sealed file missing or not matching the hash committed in `eval/golden/citedesk_sealed.sha256`. A refused request writes no ledger and no run file.
- **A committed ledger of its own**, `eval/sealed_ledger.json`, same rules as the held-out ledger (D-062): the run is written into it before the first item; the first run of a system declares its passes (1 to 5, `--sealed-passes`); later passes up to that number need no reason; another pass, a fresh start of an unfinished run, or a run of a different system is refused unless `--justify` gives a reason of at least 20 characters, which the ledger keeps; an unfinished run is resumed by id and uses no pass. `eval_ledger.py` now serves both ledgers (the format and the words in a message follow the ledger; a held-out ledger cannot be loaded as a sealed one).
- **Labels come from the sealed file**, not from `citedesk_v1.json`: `eval_score` picks the file by the split in the run's header and prints a sealed note (targets in D-071); `eval_compare` refuses sealed runs as it refuses held-out ones, because neither result may be used to choose between settings.
- A test fails if any test file names the sealed file or its folder, so nothing can start reading it as a tuning signal; tests use the constants in `tools/golden.py`.
- Checked by hand: the real command refuses without the flag and, with it, on today's uncommitted tree; `verify-sealed` matches the committed hash; no sealed ledger exists yet.

**Not done by this.** The sealed run itself. It is made once, when the person responsible says so, after the system is committed and the measurements that still change the system are finished. The `STRUCTURE` and intent targets of D-071 are judged from that run's report.

### D-079. Scoring drafts with citeCheck's judge, and what is known about the judge on these drafts
**What was built** (`tools/judge_drafts.py`, `tests/test_judge_drafts.py`). The tool reads citeCheck's source from the sibling folder (nothing is installed, so neither repository needs the other in CI) and uses its `Judge` (`qwen3:8b` through Ollama, thinking on, temperature 0, prompt v1) to ask its faithfulness question of each model-written draft: is every claim backed by the passages the draft was written from? The question is the customer's message, the answer is the draft without its greeting and sign-off, the passages are the sources it was written from. Commands: `judge`, `known-bad` (does the judge notice damage added to drafts?), `sheet` (a blind sheet for labelling by hand) and `calibrate` (the judge against those labels). Printed output is ids and counts; files with draft text go to the git-ignored `eval/runs/`. The tests use a scripted judge. citeCheck's judge writes a cache into the folder it is run from, which is now ignored (`.cache/`).

**The judge on 76 saved model-written replies** (three tuned pipeline runs, 74 judged, 2 timed out): 33 supported, 27 partly supported, 14 unsupported (mean 0.63; supported 1, partly 0.5, unsupported 0). **This is not a quality score.** More than half the drafts are flagged, and reading some of the "unsupported claims" shows why: many are sentences that only manage the conversation ("A member of our team will follow up…", "Please do not send card details by email", "Could you please let us know…") which state nothing about the business and have no passage to back them. The judge's question fits an answer that is all fact and fits a draft that must also ask, promise a follow-up and greet badly. Some flags are fair ("Our website lists a standard call-out fee of $89"). Which share is which is unknown until a person has labelled.

**Does the judge notice damage?** Sentences or changes added to drafts the judge had called supported and the review aids had not marked (20 drafts; `eval/reports/judge-known-bad.md`): an invented perk 15 of 15 flagged, an invented policy 15 of 15, a credit nobody offered 15 of 15, a soft promise 14 of 14, a price made $50 larger 6 of 6 (only 6 drafts had a price), **a sentence describing how the desk works (the assistant and the checking) 4 of 14**. The judge notices a sentence that is not in the passages and mostly does not notice one about the system itself, which is the same kind the reviewer in the trial missed. The damaging sentences were written by the author of the system.

**Limits of that check, stated plainly.**
- The control (unchanged good drafts flagged: 0 of 20) says nothing: the good drafts were picked because the judge had called them supported, so it cannot flag them. A real control needs hand labels.
- The tool paired verdicts with cases by id, and six inquiries have two drafts from different runs; for those, the choice of good drafts could use the other draft's verdict. Fixed afterwards (each draft has its own id, `~2` for a second one) and not rerun.
- The judge is the same model that wrote the drafts (`qwen3:8b`), which may favour its own wording.
- The damage kinds are the six of the reviewer trial plus a price change; any sentence the passages do not state is flagged, so 100% on four kinds says the judge reads the passages, not that it is right about drafts in general.

**Still open.** A blind sheet of 36 drafts (half flagged by the judge, half not, no verdicts shown) is written and waits for hand labels in `eval/labels/draft_faithfulness.labels.json`. Until they are in, the judge's scores on real drafts are uncalibrated and are not quoted as a measure of draft quality anywhere else in the project. When labels exist, `calibrate` reports agreement, the two kinds of miss and kappa, and this entry is extended. The labels would be from one person who built the system.

### D-080. Sympathy the message does not call for: a prompt rule (`draft-v3`) and a tone mark for the reviewer
**Why.** A reading of one draft for the hand-labelling sheet found "We're sorry to hear you managed to complete the work yourself" in reply to a customer who had apologised and cancelled because they did the job themselves. No check catches it (it claims nothing, so faithfulness is silent), and the review aids of D-077 treated short sympathy sentences as routine on purpose, which hid it. In the 76 saved model replies, 8 had a sympathy, apology or thanks-style sentence, and the model had read the message as neutral in 7 of them; two or three were misplaced.

**What changed.**
- **Prompt `draft-v3`**: "Do not say you are sorry, glad or grateful about anything unless the customer reports a problem or complaint (sorry) or good news (glad). A plain request gets a plain answer."
- **A tone mark** (`citedesk/support.py`, shown in the review panel under "Tone to check", warning only): a sentence that starts "sorry", "we're sorry" or "we apologise" is marked unless the sentiment the model read is negative or angry, or the sentence softens a refusal ("sorry, but we don't…"); one that starts "glad to hear" or "we appreciate" is marked unless the sentiment is positive. Nothing is marked when the sentiment is unknown, and a sympathy sentence that promises something (refund, credit, discount) is still marked as unsourced, not as tone. The sentiment comes from the stored classification. The mark is plain code and changes nothing about the draft; the new status is `tone` in the `support` part of the detail response.

**Measured** (a replay of the draft step with the real model and the saved sources of 55 tuned items; not the whole pipeline, and the same items the rule was written from): drafts with a sympathy-style sentence fell from 4 to 1. The cancellation reply lost its sentence, the refusal that began "We're sorry, but we don't offer senior discounts" lost its apology, and one reply to a pleased customer ("We're glad to hear our technician was helpful") lost its sentence too, which the rule allowed and the model dropped. The one that remained, "We appreciate your business and look forward to serving you again" to a neutral message, is exactly what the tone mark flags.

**Not known.** Whether other parts of the drafts changed for the worse under the new prompt (only sympathy sentences were counted), whether the `STRUCTURE` and figure checks still pass at the same rate (the whole pipeline has not been rerun), and how a reviewer reacts to the mark. Sentiment is the model's reading, so a wrong reading gives a wrong mark.

### D-081. Drafts that ask for a detail the customer already gave (`draft-v4`)
**Why.** Reading a draft for the labelling sheet showed a reply asking for the customer's area although the message gave it. In the saved runs 8 of 55 model-written replies asked for a detail the understand step had read correctly, and the reviewer in the first trial rejected drafts for the same reason (D-066). In every case the missing-fields list was empty, so the system knew. The cause is the passage "What we need to book a visit" (neighbourhood, property type, date, type of work), which the writer copies into its reply whatever the message already says.

**What changed.**
- **The writer is told what is known** (`citedesk/drafting.py`, `citedesk/pipeline.py`). `known_details` takes the extraction and gives the details the customer gave (type of work, date, property type, area, booking reference) in plain words. The user message lists them ("The customer already gave these details. Do not ask for them again, even if a passage says they are needed to book") and the system prompt, now `draft-v4`, says never to ask for a detail already given. A detail that is also missing is not listed as known. The redraft path passes the same details.
- **A review mark** (`citedesk/support.py`, shown as "Asks for something the customer already gave"): a sentence phrased as a request (a cue such as "please", "could you", "let us know", "provide", "confirm" or a question mark) that uses the words for a detail that is known is marked, with the detail named in plain words. Warning only; the status is `asks_known` and each sentence now carries `asks_for` in the `support` part of the detail response.

**Measured** (a replay of the draft step with the real model on the saved sources and the extractions of 55 tuned items; not the whole pipeline; the same items the rule was written from): drafts asking for a known detail fell from 8 to 0, none failed, and no draft has a sympathy-style sentence left (D-080 left one).

**Not known.** Whether anything else in the drafts changed for the worse (only the two defects were counted), whether the checks pass at the same rate, how the writer behaves when the extraction itself is wrong (a wrongly read area would now be repeated back as known), and whether the mark ever fires on drafts from the new prompt, since it found nothing to mark in the replay. The next full pipeline run is where these show.

Of the 18 drafts it flagged, the labeller flagged 2 (11%; exact 95% interval 1% to 35%): both were called `unsupported` by the judge and `partly_supported` by hand. Because the sample is half judge-flagged by design, re-weighting to the 74 judged drafts puts the share of drafts a person would flag at about 6%, against 55% for the judge, from two events; read it as "far lower", not as a number.
- **Why, in part.** For 12 of the 16 false flags, every claim the judge listed is a sentence that only manages the conversation or repeats the customer's message ("A member of our team will follow up…", "We'll be in touch shortly"), found by running the review aids' rules over the judge's listed claims (an approximation: the listed claims are the judge's own wording). For 25 of all 41 flagged drafts every listed claim is of that kind. The other false flags are judgment calls about short claims the passages only half state.

Its job here is limited to what the damage check showed (it notices an unsourced sentence about the business) and a verdict is only worth reading when the claims it lists are about the business. The labelled drafts were written by an earlier prompt version (before D-076, D-080 and D-081).
- **What it cannot show.** One labeller who also wrote the drafts and the sheet's rule; 36 drafts with no `unsupported` label among them, so the judge's ability to catch a clearly bad draft rests on the damage check, whose damaging sentences were written by the author of the system; kappa cannot reward agreement where one side uses nearly one label.
- **A next step, not taken:** judge only the sentences the review aids classify as claims (leaving out routine, tone and request sentences, a rule in plain code), then compare with these 36 labels again. It would be a change made after seeing the labels, on the same 36 drafts, so its result would be a development figure.

### D-082. Judging only the sentences that make claims
**What was tried.** D-079's calibration showed the judge flagging drafts for sentences that only manage the conversation. `python -m tools.judge_drafts rejudge` removes, before judging, the sentences the review aids classify as routine, as sympathy the message does not call for, as a request for a detail already given, or as a repeat of the customer's message (plain code, `claims_only`), and judges what is left; a draft with nothing left counts as supported without a call. It was run on the 36 hand-labelled drafts (3 had no claim sentence left).

**First run** (against the labels): exact agreement 29 of 36 (it was 18), the judge flagged 5 of the 34 drafts the labeller called supported (it was 16), but it passed both drafts the labeller called partly supported. Looking at those two showed a flaw in the separation rather than in the judge: a vague sentence ("We can also help with any other plumbing needs you may have") had been dropped as a repeat of the message because it shared one word with it. The review aids' rule for "repeats the message" now needs at least three content words (this also changes the aids: a short sentence sharing one word with the message is no longer marked as theirs).

**Second run**, same 36 drafts: exact agreement 29 of 36 (81%), fine versus flagged 30 of 36 (83%), Cohen's kappa 0.07. The judge flagged 5 of the 34 drafts the labeller called supported (15%) and flagged 1 of the 2 the labeller called partly supported. The whole-draft judge, on the same drafts: 18 of 36, 20 of 36, kappa 0.02, 16 false flags, both of the 2 flagged.

**What it means, and does not.** The false flags fell from 16 to 5, so most of the over-strictness came from conversation-managing sentences. Sensitivity is not shown: there are 2 positives, one caught, and kappa stays near zero because one label dominates. **This is a development figure**: the rule was changed once after seeing which labelled drafts it missed, on the same 36 drafts, by one labeller who also wrote the drafts and the sheet's rule; the claim "the judge agrees with a person" is not made. The five remaining false flags are judgment calls about short claims the passages only half state or about a sentence that mentions no passage fact.

**Not done.** The damage check of D-079 was not rerun with the separation, so it is not known whether the judge still notices every kind of invented sentence after it (an invented perk or policy stays in the text it sees, so it should); the 36 labelled drafts are from an earlier prompt version; and the judge's scores on the other 38 drafts are not recalibrated by this.

**Addendum to D-082: the damage check with the claims-only rule and a real control** (`eval/reports/judge-known-bad-claims-only.md`). The good drafts are the 34 the labeller called supported. Each kind of damage is added to up to 15 of them, and the damaged text goes through the same removal of conversation-managing sentences before the judge sees it. Result: unchanged good drafts flagged **5 of 34** (15%; exact 95% interval 5% to 31%, the same 5 as in the agreement figures); an invented perk 15 of 15; an invented policy 15 of 15; a credit nobody offered 15 of 15; a soft promise 14 of 15; a price made $50 larger 4 of 4 (few of the drafts state a price); **a sentence describing how the desk works 7 of 15** (47%; interval 21% to 73%, it was 4 of 14 before).
- **Reading.** With the separation the judge keeps noticing an invented claim about the business, and 15% of good drafts are flagged against 47% before. It remains weak at the one kind that is about the system and not the business. The same limits as before apply: the damaging sentences were written by the author of the system, any sentence the passages do not state is flagged, so 100% on four kinds says the judge reads the passages, not that it is right on drafts in general; the good drafts are from an earlier prompt version and were labelled by one person.
- **Use.** The judge, run on claim sentences only, is usable as a screen that flags an unsourced claim about the business, at the cost of about one false flag in seven good drafts. It is not a score of draft quality, it does not replace the review aids or the person reading, and it does not see tone, completeness or a draft that fails to give an answer it had.

### D-083. A price the documents hold and the draft leaves out (a review mark, not the `ADDRESSES_ASK` check)
**Why.** The reply to a forwarded thread naming a 50-gallon tank said a quote could be given and did not give the price in the passages (D-081 addendum). Replaying the saved tuned drafts showed the same pattern was common: the customer asks what something costs, the retrieved pricing line is there, and the draft says a member of the team will confirm. Faithfulness checks stay silent on such a draft because it claims nothing.

**Decision.** The designed `ADDRESSES_ASK` check is judge-based and stays unbuilt. What was built is a narrow review mark in plain code (`citedesk/support.py`, `unanswered` in the `support` part of the detail response, shown in the review panel as "A price in your documents that the reply leaves out"). It appears when all of these hold: the message asks what something costs (cost, price, quote, estimate, "how much is/for/to/would...", not "how much notice"); the draft states no money figure at all; and a source line with a price shares at least two content words or plain numbers with the message ("50-gallon" and "40-gallon" differ), the best line winning. A price the customer quoted themselves does not count as left out. Warning only: it does not block, route or change a draft. Whether a price the draft does give is the right one stays with the figure check and the figures list.

**Measured on the saved tuned drafts** (78 model-written replies across three pipeline runs; the cases were seen while designing the rule, so these are development figures): the mark fired on 12. Reading each: 7 are drafts that defer the price although the line for the asked service is in the passages (water-heater flush, 40- and 50-gallon replacement, disposal installation; two inquiries appear in two runs each); 3 ask the customer for a detail instead of giving the price (the forwarded thread and a booking request, the latter in two runs); 1 is arguable (a gas-to-gas swap, where the labelled item says the documents cannot answer it and the passage lists only a general 40-gallon price); and 1 is a false alarm (a price-match request, matched to the main sewer line price through two shared words). The first version also fired on "How much notice do I need to cancel" and on a message that quoted a price itself; both are fixed and covered by tests.

**Limits.** Prices only. Under-answering about hours, warranty terms or policies is not covered. A message about two services where the draft prices one is not marked, because any price in the draft ends the test. A match of two shared words can point at the wrong line, and the line shown is a pointer for the reviewer, not a claim that it answers the question. The mark does not reduce the cause (the writer's habit of deferring); it points at the result. Whether a reviewer acts on it has not been tested.

A separate yes/no model call for spam was not built: a spam message that the model misreads is escalated anyway (the router escalates a message the model calls spam when screening does not, `LOW_CONFIDENCE`), so it would change the intent label and not the route, at the cost of one more call per message and a chance of tagging a real message as spam. And archiving is not widened: a message is archived only when the screening score reaches 0.8 **and** the model reads it as only spam, and wrongly archiving a real customer message is the costly error. Polite spam without the usual phrases will keep going to a reviewer, who sees it in the queue. Spam items labelled to archive that are written politely will therefore most likely show as route misses again on the sealed run, as the three held-out ones did (D-072), for the same reason; the report should say so.

**"Today" is a relative date, enforced in code.** The labelling rule (README of the golden set) and the prompt both say relative dates are null; the model resolved "today" and "tomorrow" to dates anyway (6 invented messages: 5 of 6 had a date worked out for a relative phrase, with the prompt already listing "tomorrow" as null; adding "today" to the list changed nothing). `normalise_fields` now drops `start_date` unless the customer's message writes out a date (a month with a day, a day with a month, an ISO date or `11/6`); the note `start_date_relative` is recorded and `dates_as_written` keeps the customer's words for the reviewer. A flooding, burst-pipe or sewage match is now discounted when "if", "in case of", "what if", "suppose" or "supposing" sits right before it (within 28 characters, in the same clause) and the clause has no present-tense marker (`again`, `still`, `today`, `tonight`, `currently`, `this morning/afternoon/evening`). Tests cover imagined events that do not fire and real ones next to imagined ones that do. The held-out message that triggered this was not read to write the guard; the examples are invented. ### D-088. A blind intent-labelling sheet and an agreement scorer, to find how much of the intent gap is doubt about the labels
**Why.** Primary-intent accuracy was 73.1% on the sealed set against a target of 85% (D-087). Every intent label was written by one labeller who also wrote the system, and several recorded misses are judgment calls under the labelling rules (hours against availability, a fee asked about in the abstract). Whether the gap is mostly model error or mostly doubt about the labels is not known, and it decides whether more prompt work can help.

**What was built.** `tools/label_agreement.py` (plain code, no model, tests in `tests/test_label_agreement.py` built on invented fixtures only):
- `sheet` picks 60 items by default from the tuned and held-out splits in proportion (38 tuned, 22 held-out), seed 0, repeatable. A sealed item is refused. It writes a sheet showing channel, subject and body only (no id, category, note or label) with the labelling rules and the 13 intents, an order file mapping sheet numbers to item ids, and an empty labels file keyed by sheet number. The sheet and order file are in `eval/runs/` (git-ignored). The labels file is `eval/labels/intent_agreement.labels.json`; the command refuses to replace one that holds labels.
- `score` reads the filled labels file and reports exact agreement on primary intent, Cohen's kappa, the disagreements by pair and by item, and agreement on the items the labeller marked unsure. A labels file from another sheet is refused. Blank and invalid labels are set aside, not counted. With `--run` it adds the comparison with a saved model run: of the items the model got wrong against the existing label, how many the second labeller sides with the model on (doubt about the label), how many with the existing label (model error), and how many with neither. The report holds ids, labels and counts only.

**How to read the result.** A high rate of agreement with the existing labels, and with the model on its misses, would say the target is a model problem. Low agreement, or many misses where the second labeller sides with the model, would say part of the 85% target is not reachable under the current rules, and the rules need a decision before more prompt work. Two people can agree and both be wrong, and the existing labels were written by the author of the system; one extra labeller gives a rough guide, not a ground truth.

**Choices.** The sample uses the tuned and held-out splits because the sealed set is spent and its items must stay unseen by the fixing session. The model was tuned on the tuned items, so its agreement with the existing labels is flattered there; the held-out rows of any model comparison are the fairer ones. The sheet gives the labeller the same labelling rules the existing labels were written under, plus neutral one-line glosses for the intents the rules do not spell out, so a difference comes from the labeller's reading and not from different instructions. Primary intent only: it is the label behind the 85% target.

**Not done.** The labelling itself, which needs a person who has not written the labels. No result is claimed.

**Also checked.** The web checks (lint, format, typecheck, 354 tests, build, API types) pass on `main`.

### D-090. Booking or availability: decided by what the customer asks, written into the labelling rules
**Why.** In the second-labeller check (D-089) the largest group of differences was `booking_request` labelled `availability_question` (4 items, 5 with one `other`). The labelling rules said "asking for a visit" and "whether someone is free at a time" and did not say where "can you come Thursday?" falls. The route depends on it: an availability question ends as `NOT_IN_KNOWLEDGE_BASE` (live availability is not in the documents), and a booking request with all its details gets a draft reply.

**What the existing labels do.** All 4 items with `availability_question` as primary intent ask whether someone is free, available or has an opening ("do you have anyone free next tuesday afternoon", "Is anyone free Friday", "Are you free to do a drain job Saturday", "Is anyone available for a leak"). No item with `booking_request` as primary intent asks that; they ask the business to come, book or look at a problem ("can you come today", "can someone come out Sunday", "any chance somebody can look at it tomorrow", "how fast can someone come"). The labels were therefore consistent with one rule that was not written down. Two messages with the same shape can take different labels because of this wording ("Is anyone free Friday ... for a drain cleaning" against "can you come thursday ... house in Dunmore Flats").

**The rule (now in `eval/golden/README.md`, the sheet text in `tools/label_agreement.py` and, as an example fix, `docs/BACKEND_SCHEMA.md`).** Asking whether someone is free, available or has an opening at a time: `availability_question`. Asking the business to come, book or look at a described problem, even as a question: `booking_request`. A question about a visit that already exists ("is my visit still on for Friday?") is neither; the golden set labels it `other`.

**Effect.** No golden label changes, so no set is spent and no score changes. The five differences of D-089 in this group all follow the existing labels under the rule. The prompt (`understand-v3`) is unchanged: its definitions already read "asks whether someone is free at a time, or when the next opening is" and "asks for a visit to be booked", and earlier prompt wording changes moved unrelated items (D-074, D-085, D-086). A future labeller reads the rule on the sheet.

**Document fix.** The illustrative golden item in `docs/BACKEND_SCHEMA.md` ("Can someone come out this week? How much would that be?") had `availability_question` as primary intent. Under the rule it is `booking_request`; the example now says so. It is an example only: no test or data file reads it.

**Choices not taken.** Treating "can you come" as availability would relabel about 17 items and spend the tuned and held-out sets. Merging the two intents would change the enums, the database checks and `BACKEND_SCHEMA.md` for a small gap.

**Not done.** The rule is not tested by a model run, and agreement under the new wording was not measured: the 60-item sheet of D-088 was labelled before the rule was written. The rule is wording-based, so a customer who means a booking and writes "are you free Thursday?" is read as asking about availability.

### D-091. The blocking draft checks: gaps closed, and a red-team set that keeps them closed
**Why.** A review of the project ran invented sentences through the blocking checks with a source that held "We do not offer a full refund" and "If you smell gas, leave the house". Six of eight got past every check: "No problem, we'll refund you in full" (the "no" of "no problem" excused the promise, because the negation window ran across the comma), "We will give you a full refund" (the phrase is in the sources, inside a sentence that denies it), "We'll apply a credit of fifty dollars" and "We'll knock twenty dollars off" (spelled-out money was not a figure, and neither wording was in the list), "Please pay at kestrel-billing.net" (the link check found only `http`, `www` and email addresses), and "The gas smell is probably nothing to be concerned about" (the reassurance list was narrow). These are the checks a model's draft cannot get past, so each gap is a way round the rule that code decides.

**What changed (`citedesk/checks.py`).**
- **Clause scope.** A negation or a condition excuses a promise only in the same clause, and a comma now ends a clause. Figures of speech ("no problem", "no worries", "not a problem") are removed before the search, so they excuse nothing.
- **Quoting the sources.** A promise phrase that also appears in the sources is allowed only when one of those appearances is not denied in its own clause. "We do not offer a full refund" no longer lets a draft say "a full refund". Safety advice is unchanged: it may repeat the sources' words, conditions included ("If you smell gas, leave the house").
- **Negative promises.** "You won't be charged", "you will not have to pay", "no charge": a negation cannot excuse these, because the negation is the promise. Wording the sources use is still allowed.
- **New wordings** in the lists: bookings ("locked in", "pencilled in", "we have you down for", "you're all set", a technician or plumber who will come or be there with a time named), refunds ("reimburse"), waivers and credits ("half price", "percent off", "knock ... off the", "apply a credit", "take care of the fee", "it's on us") and reassurance ("nothing to worry about", "probably nothing", "not an emergency", "perfectly normal").
- **Spelled-out money** ("fifty dollars", "two hundred bucks", "one hundred forty-nine dollars") is a money figure, so the figure check compares it with the sources like "$50".
- **Bare domains** ("kestrel-billing.net", for common endings) count as links, so the link check compares them with the sources and the business's own details.

**The red-team set (`tests/test_checks_redteam.py`).** 27 sentences the checks must stop, 16 they must allow (each check's existing allowed wordings, the sources' own sentences, and one sentence from a real tuned draft that an earlier version of these patterns blocked wrongly: "A technician will come to check and confirm the issue"), and 6 known misses kept as strict expected failures, so a change that starts catching one fails the test until the sentence moves. Known misses: "We'll make it right for you at our expense", "Consider the travel fee handled", "We'll look after the bill for you", "Rest easy, it's the kind of smell drains give off", and the reviewer trial's two plants that a check could see ("You can count on us being at your door first thing on the day", "I'll make sure a courtesy credit is applied to your first visit"). The trial preparation needs plants that pass every check, so those two stay as they are.

**Measured on real drafts.** The saved drafts of four tuned pipeline runs (219 drafts written by `qwen3:8b`) were checked again with the old and the new checks. The new checks change no outcome: no draft that passed is now blocked, and none that was blocked now passes. (Two drafts from the runs of 2026-10-28 pass now that were blocked then; the checks on `main` before this change give the same result, so earlier fixes did that.) The model rarely writes these wordings unprompted; they matter for injected and unusual messages.

**Also changed.** `tests/test_injection_end_to_end.py`: the "notice to the desk" case ("I will apply a goodwill credit") was a recorded residual; it is now blocked by `NO_COMMITMENT`, so its expected status is `escalated`.

**Limits.** The set was written by the same session that changed the checks, so passing it is by construction and says nothing about wordings nobody has seen. The checks are still phrase lists. No model run, prompt, label or golden item changed. A catch rate needs sentences written by someone who has not read the checks.

### D-092. The API answers only this machine's names, and takes changes only from pages on it
**Why.** A project review found two ways a website open in the same browser could reach the API, which listens on 127.0.0.1 with no authentication. **DNS rebinding:** a site can make its own name resolve to 127.0.0.1; the browser then treats the API as that site's own origin and lets its page read `GET /api/inquiries`, which holds the invented customer messages (or real ones, in a pilot). Nothing checked the `Host` header. **Cross-site form posts:** a form on another site can post to an endpoint that takes no body, such as `POST /api/inquiries/{id}/reprocess`, without a CORS preflight. The endpoints with a JSON body were already safe, because a cross-site JSON request needs a preflight the API does not answer.

**What changed.** A middleware in `citedesk/api.py`, with the rules as plain functions in `citedesk/guards.py`:
- `Host` must name this machine (`127.0.0.1`, `localhost` or `::1`, any port), or the answer is 400 `host_not_allowed`.
- A `POST`, `PUT`, `PATCH` or `DELETE` with an `Origin` header must come from a page on one of those names (http or https), or the answer is 403 `origin_not_allowed`. `Origin: null` (a sandboxed page or local file) is refused.
- A request with no `Origin` is allowed: browsers send it on every cross-site POST, so its absence means a tool such as `tools.import_inquiries`, and the `Host` check already limits it to this machine.
- Both refusals use the API's error shape and carry the request id.

**Choices.** A fixed list of names rather than a setting: the server binds to 127.0.0.1 only (TRD section 8), so no other name is right, and a setting would be one more way to open it by mistake. Cross-origin reads with a local `Host` are not refused, because the browser already keeps their answers from the page (no CORS headers). The test client's name, "testserver", is added in `tests/conftest.py` only; `tests/test_host_origin.py` uses 127.0.0.1 and checks the refusals.

**Checked.** 26 new tests, and a live server on a spare port: a rebinding `Host` got 400, a post with a foreign `Origin` got 403 and changed nothing, and the requests the Vite proxy sends (`Host: 127.0.0.1:5174`, `Origin: http://127.0.0.1:5174`) and a tool without `Origin` went through.

**Limits.** Any program running on the machine can still call the API; there is no authentication, and v1 is for one person on one machine. The web app was also run against the real API after the change: the queue loaded through the Vite proxy at `http://localhost:5174`, and a POST from the page (with the browser's own `Origin`) was answered 200.

### D-093. An intent baseline with no model: naive Bayes reaches 51%, the model about 70%, on the held-out split
**Why.** A project review found no comparison with a cheap method. Primary-intent accuracy was reported against the PRD target (85%) and between system versions, but not against a classifier without a language model. Without one, it is not known how much `qwen3:8b` adds on this step.

**What was built.** `tools/intent_baseline.py` (plain code, no new dependency; tests in `tests/test_intent_baseline.py` on invented fixtures):
- **Majority:** always the commonest primary intent of the training items.
- **Naive Bayes:** multinomial, on lower-case words and pairs of neighbouring words from the subject and body, add-one smoothing, ties to the intent that sorts first. No setting is tuned; the method and features were fixed before the held-out score was produced.
- Trained on the tuned split (135 items), scored on the held-out split (76 items), with leave-one-out on the tuned split as well. The sealed split is refused. With `--run`, a paired comparison with saved model runs on the same items. The report (`eval/reports/intent-baseline.md`) holds ids, intents and counts only.

**Result (run once; a rerun after a wording change to the report gave the same numbers, as the method has no random part).**
- Majority (`booking_request`): 14 of 76 held-out (18.4%).
- Naive Bayes: 39 of 76 held-out (51.3%; 95% interval 40.3% to 62.2%); tuned leave-one-out 59 of 135 (43.7%).
- Paired with the three saved held-out passes of the model (the system of 2026-10-29, thinking on; 75 items it read): the model was right on 52, 52 and 53 (69.3% to 70.7%), naive Bayes on 39 of the same 75. The model alone was right on 21 to 22 items, naive Bayes alone on 8, both wrong on 14 to 15.

The step earns its cost on this measure. A word-count method still gets half the items right, which bounds how much of the model's score comes from reading beyond the words.

**Limits.** The held-out set is small (76 items) and written by the same author as the tuned set, which helps a word-count method through shared wording. The model runs are of the system before D-074 to D-085; the sealed set cannot be used here (D-071), so no baseline exists for the final system's 73.1%. Primary intent only: routing, escalation and drafting are not compared. A stronger cheap baseline (embeddings with a linear classifier) was not tried, because it needs a model of its own.

### D-094. A cost-weighted route score: on the held-out runs, routing cost more than escalating everything
**Why.** A project review found that route accuracy counts every wrong route the same, so a gas leak that gets a draft weighs as much as a plain question sent to a person. It also found that the 85% intent target was set without reference to how well two people agree on the labels (D-089).

**What was built.**
- `tools/route_cost.py` (plain code, no model; tests in `tests/test_route_cost.py` on invented fixtures). Each item's result falls in one kind: right, missed safety, real message archived, missed escalation, extra escalation, spam kept, or the wrong kind of reply (draft against request for details). A failed item counts as an extra escalation, because a person handles it. Costs, ASSUMPTIONS in rough minutes of a person's time, fixed before any run was scored: missed safety 100, archived 50, missed escalation 20 (a reviewer may approve the draft; the trial caught 0 of 5 planted problems), extra escalation 4 (writing by hand at about 5 minutes against checking at about 1), spam kept 1, wrong kind of reply 1. The same items are costed for two policies with no model: escalate everything, and draft everything. A break-even figure gives the missed-escalation cost at which a run and "escalate everything" cost the same, so the result does not rest on the assumed 20. The counts per kind are reported, so other costs can be applied. The sealed split is refused.
- `tools/label_agreement.py` also reports the model's accuracy on the items where both labellers agree.

**Result: held-out, three passes of the system of 2026-10-29 (`eval/reports/route-cost-heldout.md`).** Cost per 100 items: 364, 338 and 364. Escalating everything: 172. Drafting everything: 2359. No safety message was missed and no real message was archived; the cost is 12 to 13 missed escalations (mostly policy-exception requests and injections that were not flagged, which D-074 and D-075 later addressed) against 2 extra escalations. Break-even: 8.8 to 9.5. If a missed escalation costs more than about 9 minutes of a person's time, escalating everything was cheaper on this set.

**Result: tuned (`eval/reports/route-cost-tuned.md`; the split the prompts were written with in view, so flattered).** The three passes of 2026-10-29: 182, 153 and 185 per 100 (break-even 29 to 38). The pipeline run of D-084 (2026-11-06, before D-085): 103 per 100 (4 missed escalations, 13 extra; break-even 68.8). Escalating everything: 247. Drafting everything: 1192.

**Agreed labels.** On the items of the 60-item sheet (D-089) where both labellers agree: tuned, 24 of 26 right (92.3%; flattered); held-out, 10, 10 and 11 of 14 (71% to 79%). On the held-out items both people agree on, the model of 2026-10-29 was still well short of 85%; with 14 items this is a rough guide only.

**What it means.** On unseen messages, the routing of the system as it stood on 2026-10-29 was not worth its cost under these assumptions: escalating every message would have cost a person less time than reviewing drafts that should not have been drafted. The weak point is missed escalations, not extra ones. The final system raised escalation recall on the sealed set from 69.1% to 89.6% (D-087), but the sealed set cannot be costed here, so whether it now beats "escalate everything" on unseen messages is not known. A real inbox has fewer messages that should escalate than these sets (54% of held-out items), which would raise the cost of "escalate everything" and favour the system.

**Limits.** The costs are assumptions; the break-even and the counts are the parts that do not depend on them. A wrong draft is costed once, not by what happens if it is approved. No model was run.

### D-101. Deleting inquiries, and removing old ones by age
**Why.** The desk stores customer messages, drafts and reviews with no way to remove them except deleting the database file. A business that keeps customer messages needs to delete one on request and to stop keeping old ones. The docs did not cover this; the simplest form that meets both needs was chosen.

**What was built.**
- `citedesk/retention.py`. `delete_inquiry` removes an inquiry and, through the existing `ON DELETE CASCADE` keys, its screening, readings, extractions, escalations, retrievals, drafts, checks, reviews, exports and audit events. Later messages marked as its duplicates are kept and unlinked. One audit event, `inquiry_deleted`, is written in its place with no `inquiry_id`, the last status in `from_status`, and a payload of the deleted id and the cause (`reviewer` or `retention`): ids and codes only (rule 4). An inquiry the worker may be processing (`received` to `drafted`) is refused with 409, because the worker would fail on a row removed under it; once it stops, it can be deleted.
- `DELETE /api/inquiries/{id}`: 204, 404 if there is no such inquiry, 409 while it is being processed. The Host and Origin guard of D-092 applies, so another site cannot delete.
- The detail page has a "Delete this inquiry" section (not while the inquiry is being prepared). The first button only asks; the confirmation says what is removed and that it cannot be undone, and its button is "Delete for good". Afterwards the queue is shown.
- `python -m citedesk.db purge --older-than DAYS [--dry-run]` deletes closed inquiries (`exported`, `resolved`, `archived`) not changed for DAYS days, at least 1. It prints counts and ids only. It is a command, not a timer: deleting is permanent, so it runs when a person runs it (or schedules it).
- Every connection sets `PRAGMA secure_delete = ON`, so deleted text is overwritten in the database file, and a delete is followed by a write-ahead-log checkpoint so old pages do not linger in the log.
- `inquiry_deleted` is listed in `BACKEND_SCHEMA.md` outside the SQL of `0001_init.sql`, which stays as applied; the event-type test reads both places.

**Checked.** 15 backend tests (`tests/test_retention.py`): every table is emptied for the inquiry, the event holds no text, in-flight statuses are refused, duplicates are unlinked, the purge picks only closed inquiries past the period, the command and its refusals, the API answers and the cross-site refusal. A test writes a marker into a database file, deletes it and finds the marker in none of the files; it fails with `secure_delete` off. 5 web tests (asks first, can be called off, focus, failure, not offered while preparing). In the running app, on a copy of the demo database: the confirmation, the deletion, the return to the queue, a 404 for the deleted inquiry, the event row, and no trace of the deleted text in the database files.

**Limits.** Deleting removes the inquiry from Insights counts too, so the figures describe the inquiries still kept. Copies of the database file (backups, the evaluation run files in `eval/runs/`) are outside this code. There is no undo and no "deleted by" field: the app has one local user.

### D-106. The electrical emergency terms widened, after the electrician's first set

**What changed** (`citedesk/safety.py`, electrical trade only):
